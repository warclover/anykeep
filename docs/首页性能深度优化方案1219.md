## 一、优化策略调整

### 为什么调整优先级？

**原方案**：P0 布局重构 → P1 懒加载
**新方案**：P1 懒加载 → P0 布局重构

**调整理由：**

| 维度         | 先做 P1 的优势                                      |
| ------------ | --------------------------------------------------- |
| **减少变量** | 卡片数量减少后，Layout Thrashing 影响自然降低       |
| **效果量化** | 分步优化可以分别测量每步收益                        |
| **风险控制** | P1 改动小（仅常量+加载逻辑），P0 改动大（布局架构） |
| **渐进增强** | 即使 P0 出问题，P1 的优化效果已锁定                 |

```
优化路径：
┌──────────────────┐     ┌──────────────────┐     ┌──────────────────┐
│  P1: 减少卡片数量  │ ──► │  P0: 优化布局机制  │ ──► │  P2: 交互体验优化  │
│  （减负）          │     │  （提效）          │     │  （打磨）          │
└──────────────────┘     └──────────────────┘     └──────────────────┘
     改动小、风险低           改动大、收益高           锦上添花
```

## 二、问题诊断

### 2.1 首页加载性能分析

**当前配置：**

- 默认分页大小：`DEFAULT_PAGE_SIZE = 24`
- 卡片视图：`PAGE_SIZE_BY_VIEW.card = 16`
- 列表视图：`PAGE_SIZE_BY_VIEW.list = 24`
- 紧凑视图：`PAGE_SIZE_BY_VIEW.compact = 32`

**现有问题：**

1. SSR 阶段无法感知视图模式，统一使用 `DEFAULT_PAGE_SIZE = 24`
2. 卡片视图首屏只需 8-12 张，却加载了 24 张
3. 虚拟滚动已实现，但首次加载仍有优化空间

### 2.2 侧边栏滑动卡顿根因分析

**当前实现存在的问题：**

```
┌─────────────────────────────────────────────────────────────┐
│                     当前布局架构                              │
├─────────────────────────────────────────────────────────────┤
│  <div className="flex">                                      │
│    ├── <AppSidebar />           ← width: 64px ↔ 192px       │
│    └── <main style={{marginLeft: displayWidth}}>            │
│           └── 主内容区域（卡片网格）                           │
│        </main>                                               │
│  </div>                                                      │
└─────────────────────────────────────────────────────────────┘
```

**问题：`margin-left` 过渡引发 Layout Thrashing**

| 属性          | 触发阶段                   | 性能影响 |
| ------------- | -------------------------- | -------- |
| `margin-left` | Layout + Paint + Composite | ⚠️ 高    |
| `width`       | Layout + Paint + Composite | ⚠️ 高    |
| `transform`   | Composite Only             | ✅ 低    |

当侧边栏从 64px → 192px 变化时：

1. **`margin-left` 变化** → 触发主内容区 Reflow
2. **主内容区宽度变化** → 触发所有卡片的重新布局
3. **卡片重排** → 每一帧都需要重新计算 N 个元素位置
4. **帧率下降** → 60fps → 30-40fps，用户感知到卡顿

**P1 对 P0 的铺垫作用**：完成 P1 后，卡片数量从"可能 100+"降至"首屏 24"，即使在旧布局下，Layout Thrashing 的影响也会显著减小。

## 四、P1：首页卡片懒加载优化（优先实施）

### 4.1 目标

- **首次加载**：仅加载 24 张卡片（用户请求的精确数量）
- **滚动加载**：到达 80% 位置时自动加载下一批
- **视图适配**：根据视图模式动态调整每批加载数量

### 4.2 当前实现分析

**已有的优秀实现：**

1. **SWR 缓存机制** (`use-bookmarks-swr.ts`)
   - ✅ Stale-While-Revalidate 策略
   - ✅ localStorage 持久化
   - ✅ 乐观更新支持

2. **虚拟滚动** (`virtual-bookmark-grid.tsx`)
   - ✅ react-virtuoso 集成
   - ✅ 80% 位置预取
   - ✅ overscan 缓冲区

3. **分页配置** (`constants.ts`)
   - ✅ 视图模式分页大小已定义
   - ⚠️ SSR 无法感知视图模式

### 4.3 优化方案

#### 4.3.1 精确控制首次加载数量

**修改 `constants.ts`：**

```typescript
// 首页首次加载数量（固定为用户要求的 24 张）
export const INITIAL_LOAD_SIZE = 24;

// 滚动加载每批数量（可以更小，提高响应速度）
export const SCROLL_BATCH_SIZE = 12;
```

#### 4.3.2 优化 SSR 数据预取

**修改 `src/app/(main)/home/page.tsx`：**

```typescript
// SSR 阶段使用精确的首次加载数量
const INITIAL_LOAD_SIZE = 24;

const getInitialBookmarks = cache(async (...) => {
  // ...
  query = query.limit(INITIAL_LOAD_SIZE);  // 精确 24 张
  // ...
});
```

#### 4.3.3 优化滚动加载策略

**修改 `virtual-bookmark-grid.tsx`：**

```typescript
const SCROLL_BATCH_SIZE = 12;  // 每次滚动加载更少数量

// 智能预取：当滚动到 80% 位置时提前加载
```

## 五、P0：CSS Grid 布局重构（P1 完成后实施）

### 5.1 架构对比

**当前架构（Flexbox + margin-left）：**

```tsx
<div className="flex">
  <aside style={{ width: displayWidth }} /> {/* 触发 Layout */}
  <main style={{ marginLeft: displayWidth }} /> {/* 触发 Layout */}
</div>
```

**目标架构（CSS Grid + transform）：**

```tsx
<div className="grid grid-cols-[auto_1fr]">
  <aside
    style={{
      width: displayWidth,
      transform: `translateX(${isCollapsed ? -128 : 0}px)`,
    }}
  />
  <main className="col-start-2" /> {/* 无需响应侧边栏宽度 */}
</div>
```

### 5.2 实现方案

#### 方案 A：CSS Grid 布局（推荐）

**修改文件：**

1. `src/app/(main)/layout.tsx` - 主布局
2. `src/components/layout/main-content-wrapper.tsx` - 内容包装器
3. `src/components/layout/app-sidebar.tsx` - 侧边栏

**核心改动：**

```tsx
// layout.tsx - 改用 CSS Grid
<div className="grid grid-cols-[auto_1fr] min-h-screen">
  <AppSidebar />
  <MainContentWrapper>
    <MainContent>{children}</MainContent>
  </MainContentWrapper>
</div>
```

```tsx
// main-content-wrapper.tsx - 移除 marginLeft
<main className="col-start-2 min-w-0 p-4 md:p-6 pb-20 lg:pb-6">{children}</main>
```

```tsx
// app-sidebar.tsx - 使用 transform 代替 width 过渡
<aside
  style={{
    width: SIDEBAR_WIDTH.expanded,  // 固定宽度
    transform: `translateX(${isCollapsed && !isHoverExpanded ? -(SIDEBAR_WIDTH.expanded - SIDEBAR_WIDTH.collapsed) : 0}px)`,
    willChange: "transform",
  }}
  className="transition-transform duration-200 ease-[cubic-bezier(0.4,0,0.2,1)]"
>
```

**优点：**

- ✅ 完全消除 Layout Thrashing
- ✅ 侧边栏动画帧率稳定 60fps
- ✅ 主内容区无需响应侧边栏变化

**缺点：**

- ⚠️ 需要修改 3 个核心布局文件
- ⚠️ 需要充分测试响应式布局

---

#### 方案 B：双层结构 + transform（备选）

保持现有 Flexbox 结构，仅优化侧边栏动画：

```tsx
// app-sidebar.tsx
<div
  style={{ width: SIDEBAR_WIDTH.expanded }}
  className="relative overflow-hidden"
>
  <aside
    style={{
      transform: `translateX(${isCollapsed ? -(SIDEBAR_WIDTH.expanded - SIDEBAR_WIDTH.collapsed) : 0}px)`,
    }}
    className="absolute inset-0 transition-transform duration-200"
  >
    {/* 侧边栏内容 */}
  </aside>
</div>
```

**优点：**

- ✅ 改动较小，仅修改侧边栏
- ✅ 侧边栏内部动画流畅

**缺点：**

- ⚠️ 主内容区仍需响应 margin-left
- ⚠️ 无法完全消除 Layout Thrashing

### 5.3 推荐方案

**选择方案 A（CSS Grid）**

理由：

1. 从根本上解决问题，而非局部优化
2. 一次性投入，长期收益
3. CSS Grid 现代浏览器兼容性良好（> 97%）
4. **P1 完成后卡片数量已减少**，即使出问题影响也更小

## 六、P2：交互体验优化

### 6.1 滚动加载指示器

**用户反馈机制：**

```tsx
// 底部加载指示器
{
  isLoadingMore && (
    <div className="flex items-center justify-center gap-2 py-4">
```
