# 文件夹创建优化方案 0225

**文档版本**: 1.0  
**日期**: 2026-02-25  
**角色视角**: AnyKeep CTO · 项目全局  
**状态**: 待审核

---

## 一、问题与目标

### 1.1 现象

用户短时间内连续收藏同一主题内容（以「一人公司 / OPC」居多）时，系统自动创建了 **2 个** 文件夹，且两个文件夹均为同一主题，理论上应归入 **同一文件夹**。

### 1.2 目标

- **主目标**：同一主题在短时间内的多次收藏，优先归入已有文件夹，避免因「名称表述不同」或「冷启动」导致过度拆分。
- **约束**：不改变现有「高置信度自动归类」「建议新建」的主流程形态，仅在**创建前决策**与**命名/匹配**上做增强。

### 1.3 成功标准

- 同一主题（如 OPC/一人公司）在 **24 小时内** 的多次收藏，**多数** 进入同一自动创建文件夹，或匹配到该主题已有文件夹。
- 自动创建文件夹数量（尤其是同日、同主题）**明显减少**，且不降低「正确归类」率。

---

## 二、根因摘要

| 维度           | 现状                                                       | 导致的问题                                                 |
| -------------- | ---------------------------------------------------------- | ---------------------------------------------------------- |
| **创建前检查** | 仅用**名称字符串相似度**（≥0.8 拒建）                      | 「一人公司」「OPC 创业」等语义同、字面不同，无法合并       |
| **AI 命名**    | 每次仅根据**当前书签**生成名称，无「最近创建文件夹」上下文 | 同一主题不同文章得到不同名称（如「一人公司」「个人创业」） |
| **匹配范围**   | 仅用**已有文件夹**的 profile/name 做向量检索               | 刚创建的文件夹 profile 未更新，后续一条无法命中            |
| **时序与批量** | 每条收藏独立决策，无「近期创建」或「待合并」概念           | 连续两条都判为「无匹配 → 建议新建」→ 两个新文件夹          |

---

## 三、方案总览

在**不推翻现有分类架构**的前提下，做三块增强：

1. **创建前：语义相似 + 近期文件夹优先**  
   在 `AutoCreateEvaluatorService` 中，对「建议新建」的名称/主题做**语义相似**检查，并引入**近期创建文件夹**（如 24h 内）列表，名称或语义任一相似则**拒建并返回已有文件夹**。
2. **命名与匹配：AI 考虑近期文件夹**  
   在 `SimpleClassificationService.aiCreateFolder` 与（若使用）`folder-recommender` 中，传入**近期创建的文件夹名列表**，Prompt 中要求「若与下列名称主题一致，优先复用该名称」。
3. **新建后：快速纳入匹配**  
   新建文件夹后，在**同一次请求或异步**中尽快更新 folder profile（或至少 name embedding），使紧接着的下一条收藏能命中「刚建的文件夹」。

可选（后续迭代）：**短时合并窗口**（例如 5 分钟内「建议新建」先入待定池，再按主题聚合后真正创建）。

## 四、可落地实现方案

### 4.1 Phase 1：创建前语义相似 + 近期文件夹（推荐先做）

**目标**：在决定「是否创建新文件夹」时，不仅看名称字符串，还看**语义**与**近期是否已有同主题文件夹**。

**涉及文件**：

- `src/lib/classification/services/advanced/auto-create-evaluator.service.ts`
- `src/lib/classification/constants/limits.ts`（可选：新增常量）

**实现要点**：

1. **近期文件夹列表**
   - 在 `evaluate()` 内，除 `getUserFolders(userId)` 外，增加一次查询：`getRecentlyCreatedFolders(userId, hours = 24)`（按 `created_at` 筛选）。
   - 将「近期文件夹」与「全部文件夹」合并去重后，用于后续相似度检查（近期文件夹可设**更宽松**的相似度阈值，见下）。

2. **语义相似度**
   - **方案 A（无新依赖）**：用现有 **folder profile 的 embedding**：对 `proposedName` 生成 embedding，与近期文件夹的 **name_embedding** 或 profile embedding 算余弦相似度；若任一 ≥ 阈值（如 0.72），则 `shouldCreate: false`，`similarFolder` 返回该文件夹，由上层归入该文件夹。
   - **方案 B（轻量）**：若暂时没有 name_embedding，可用 ** 通用分类 + 标签关键词**：用 `matchCategoriesByKeyword(proposedName)` 与 `bookmarkTags` 得到「主题 id」；近期文件夹若同名主题或标签重叠高，则视为同主题，拒建并返回该文件夹。

3. **阈值策略**
   - 现有：名称相似度 ≥ 0.8 → 拒建。
   - 新增：**近期文件夹**（如 24h 内）名称相似度 ≥ **0.65** 或语义相似度 ≥ **0.72** → 拒建并返回该文件夹；非近期仍保持 0.8 名称阈值，避免误合并老文件夹。

4. **常量**
   - 在 `limits.ts` 中增加，例如：`RECENT_FOLDER_HOURS = 24`、`RECENT_FOLDER_NAME_SIMILARITY = 0.65`、`RECENT_FOLDER_SEMANTIC_SIMILARITY = 0.72`（若用 embedding）。

**集成**：

- 在 `integration.ts` 中，当分类结果为 `suggest_new` 且要执行「自动创建」前，若已走 **AutoCreateEvaluatorService**（需确认当前 V4.1 是否每条都调），则评估结果若为 `shouldCreate: false` 且带 `similarFolder`，应**归入 similarFolder** 而不是再建新文件夹。
- 若当前 V4.1 主流程未调用 `AutoCreateEvaluatorService`，则需在「高置信度 + suggest_new」分支中**先调** `evaluate(userId, result.folderName, result.confidence, bookmarkTags)`，再根据 `evaluate` 结果决定是创建新文件夹还是归入 `similarFolder`。

---

### 4.2 Phase 2：AI 命名考虑「近期创建的文件夹」

**目标**：让 AI 在生成「新文件夹名」时，知道用户最近刚建了哪些文件夹，若当前书签与其中某个同主题，则**直接复用该名称**，从源头减少「同主题不同名」。

**涉及文件**：

- `src/lib/classification/services/simple-classification.service.ts`（`aiCreateFolder`）
- 可选：`src/lib/ai-generator/folder/folder-recommender.ts`（若分类流程中有用）

**实现要点**：

1. **获取近期文件夹名**
   - 在 `aiCreateFolder()` 内，根据 `userId` 查询近期（如 24h）创建的文件夹，取 `name` 列表（如最多 10 个）。

2. **Prompt 增强**
   - 在现有「根据书签内容生成 2–6 字文件夹名」的 prompt 后追加一段，例如：  
     「用户最近创建的文件夹名称如下：[A, B, C]。若当前内容与其中某个**主题一致**，请**直接返回该文件夹名称**，不要创造新名称。仅当与上述皆不同主题时，再生成新名称。」

3. **返回值与上层逻辑**
   - AI 若返回的是「已有文件夹名」，当前实现会得到 `folderName: "某名"` 且 `folderId: null`。
   - 在 **integration** 层：在真正执行「创建新文件夹」前，用**现有逻辑**（或 Phase 1 的 evaluator）根据该 `folderName` 解析出是否已存在文件夹；若存在，则**归入该文件夹**而不是再 insert 新文件夹。
   - 这样 Phase 1 与 Phase 2 可叠加：Phase 1 负责「创建前拦截」，Phase 2 负责「命名阶段就尽量复用」。

---

### 4.3 Phase 3：新建后快速参与匹配（减少冷启动窗口）

**目标**：新文件夹创建后，**尽快**让其参与向量/名称匹配，这样紧接着的同主题收藏能命中「刚建的」文件夹，而不是再次触发「建议新建」。

**涉及文件**：

- `src/lib/classification/integration.ts`（创建文件夹成功后）
- `src/lib/classification/folder-profile-manager.ts`（或当前更新 folder profile 的模块）

**实现要点**：

1. **创建后同步更新 profile**
   - 在 `integration.ts` 中，当 `insert folders` 成功并 `update bookmarks.folder_id` 后，**同步调用**现有的「更新该文件夹 profile」逻辑（如 `updateFolderProfile(newFolder.id, userId)`），确保 name_embedding 和（若有）content profile 尽快写入。
   - 若已有「创建后异步更新」的调用，可改为**同步**仅针对「本次请求新建」的文件夹，或缩短异步延迟（如 0ms 队列），避免下一条请求在 profile 未写好时就执行检索。

2. **name_embedding 必写**
   - 新建文件夹时，若 DB 有 `name_embedding` 字段，应在创建 folder 时或紧随其后的 profile 更新中，用 `folder.name` 生成 embedding 并写入，这样 `search_folders_unified` 才能立即用名称匹配到新文件夹。

3. **可选：新文件夹在检索中的权重**
   - 若 `search_folders_unified` 中有「按 bookmark_count 或 created_at 加权」的逻辑，可对「最近 1h 内创建且 bookmark_count ≤ 2」的文件夹略提高权重，减少「因书签少、分数略低」被截断在 topK 之外的情况（需在 DB/RPC 或应用层实现，量力而行）。

---

### 4.4 可选：短时合并窗口（后续迭代）

**思路**：在 5 分钟内，若多条收藏都得到「建议新建」且 AI 返回的文件夹名**语义/名称相似**，可只创建**一个**文件夹，把这些书签都归入其中。  
**复杂度**：需要「待建文件夹」的临时存储（如 Redis 或 DB 表）、定时或事件驱动聚合、以及「延迟写入 folder + 批量更新 bookmarks」。  
**建议**：Phase 1–3 上线并观察「同主题多文件夹」是否已明显下降后再考虑；若仍多，再设计该方案。

## 五、配置与开关

- 所有「近期」相关时间窗口（如 24h）建议放在 `limits.ts` 或 feature flags 中，便于调参与回滚。
- Phase 1 的「语义相似」若依赖 embedding，需确认 **embedding 服务** 在创建评估路径上的延迟与可用性；若不可用，可先仅用「近期文件夹 + 名称相似度 0.65」上线。

## 六、测试与验收

- **单测**：
  - AutoCreateEvaluator：传入「近期创建的文件夹」列表，提议名与其中一名语义/名称相近，应返回 `shouldCreate: false` 且 `similarFolder` 正确。
  - AI 命名：mock 近期文件夹名包含「一人公司」，当前书签标签为 OPC/一人公司，期望 AI 返回「一人公司」或已有名。
- **集成/手工**：
  - 连续收藏 3–5 篇同主题（如 OPC）文章，期望：至多 1 个新文件夹被创建，其余归入该文件夹或已有同主题文件夹。
- **回归**：
  - 不同主题的连续收藏仍应创建不同文件夹；非近期、不同名文件夹不应被误合并。

## 八、风险与回滚

- **误合并**：近期文件夹阈值过松会导致不同主题被归入同一文件夹。缓解：先用保守阈值（如 0.72 语义、0.65 名称仅对近期），灰度观察；回滚可关掉「近期文件夹」或仅保留名称相似 0.8。
- **依赖 embedding 的延迟**：若 Phase 1 用 embedding，evaluate 路径会增加一次 embedding 调用；可接受则保留，否则先上「近期 + 名称 0.65」。
- **AI 返回已有名**：Phase 2 中 AI 可能错误地把不同主题归为已有名，需在 integration 层用「名称/语义相似度」再校验一次，只有真正匹配才归入，否则仍创建新文件夹。
