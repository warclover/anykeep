# AnyKeep 主页面响应速度与卡顿 — 诊断与优化方案

> 文档版本：1.0  
> 目标：改善主要页面（首页/收藏、分类、搜索等）的响应速度与操作卡顿感，便于评审与排期。

---

## 一、现状与问题归纳

### 1.1 已做的优化（基线）

- **首页**：Streaming SSR + Suspense、React `cache()`、`unstable_cache` 用户设置、SWR 客户端缓存、虚拟列表（react-virtuoso）。
- **布局**：主布局用 Suspense 边界、LayoutAIPanel/FloatingActionMenu 用 `Suspense fallback={null}`、V5.3 桌面/移动条件渲染。
- **首页组件**：VirtualBookmarkGrid/List、HomeDialogs、BatchTagDialog、SynthesisRecommendBubble 等已 lazy；BookmarkCard 已 memo；Home 相关 Context 已拆成 5 个（ViewMode/Filter/Dialog/Selection/AIPanel）。
- **数据**：书签 SWR、staleTime/cacheTime 配置、localStorage 持久化、useProcessingPoller 可见性检测。

### 1.2 可能导致“慢”和“卡”的根因（按优先级）

| 类别                | 现象                                   | 可能原因                                                                                                                                                                        |
| ------------------- | -------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| **首屏/导航慢**     | 进入首页或切 Tab 要等一会              | 首页 `force-dynamic` 全量服务端执行；RSC 串行查 bookmarks + userSettings；无 SSR 时 initData + SWR 双重/条件请求；Folders 服务端一次查 folders + RPC + recentBookmarks 体量大。 |
| **操作卡顿**        | 筛选、排序、切换视图、滚动时有明显卡顿 | Context 订阅过多，任一更新导致 HomeView/列表整树重渲染；Virtuoso 的 `itemContent` 等用内联函数，引用不稳；部分回调未 useCallback，memo 失效。                                   |
| **列表滚动/加载卡** | 大列表滚动不跟手、加载更多时卡         | 虚拟列表 overscan 或 item 高度估算不当；单卡片渲染过重（BookmarkCard 内逻辑/依赖多）；加载更多时整列表 setState。                                                               |
| **后台持续开销**    | 不操作也偶发卡一下                     | 轮询（Processing 轮询 3s、分类轮询）、多处 refetchInterval；SWR 后台 revalidate 触发整列表更新。                                                                                |
| **布局/渲染成本**   | 侧栏折叠、窗口 resize 时卡             | 主内容区 `willChange: margin-left` 常驻；transition 触发重排/重绘；Suspense 多次 resolve 导致布局抖动。                                                                         |

---

## 二、优化方案总览

- **P0（优先）**：减少首屏/导航的阻塞与重复请求；降低 HomeView/列表的无效重渲染。
- **P1**：虚拟列表与卡片渲染、滚动与加载更多体验。
- **P2**：轮询与后台刷新策略；布局与动画对主线程的影响。

---

## 三、P0：首屏与数据加载

### 3.1 首页：减轻 RSC 与重复请求

**问题**

- `export const dynamic = "force-dynamic"` 导致每次请求都走完整服务端。
- 同一请求内 `getInitialBookmarks` 与 `getUserSettings` 若未并行或复用，会拉长 TTFB。
- 无 SSR 初始数据时，`HomeDataProvider` 内 `useInitData` 与 `useBookmarksSWR` 的条件组合可能造成“先聚合再按条件再请求”的多次水合后请求。

**建议**

1. **并行请求**：在 Home 的 async 数据层并行 `getInitialBookmarks` 与 `getUserSettings`（同请求内用 `Promise.all`），避免串行等待。
2. **放宽 dynamic**：评估是否对首页去掉 `force-dynamic`，改用 `revalidate`（例如 60）或按 cookie/session 做短时缓存，减少重复的完整 RSC 执行。
3. **统一一条主路径**：明确“有 SSR 初始数据时仅做 hydration + SWR 静默 revalidate；无 SSR 时仅一条主请求（init 或 SWR）”，避免同一场景下两条数据源竞态或重复请求。

**验收**

- 首屏 TTFB / LCP 下降（可配合 Web Vitals）。
- 水合后不必要的书签/设置二次请求减少或消失。

### 3.2 首页：SmartList 与默认参数

**问题**

- URL 带 `smartList` 时走 SmartListView，不再预加载书签；其他情况会走 `getInitialBookmarks`。若默认参数（platform/sort/folder）与用户习惯不一致，可能首屏就触发一次“无效”的 SSR 查询。

**建议**

- 对“无 platform/folder/sort”的默认首页，考虑只取极少条数（如 1 页）或仅返回骨架数据，把完整列表交给客户端 SWR，缩短服务端计算时间。
- 若存在“默认智能列表”，可考虑与 SmartList 分支一致，首屏只渲染壳，数据由客户端拉取。

### 3.3 Folders 页：服务端一次加载

**问题**

- 服务端串行/并行查：folders、`get_folder_bookmark_stats` RPC、folder_profiles、categories、recentBookmarks。数据量大时 RPC 和多次 round-trip 会拖慢首屏。

**建议**

1. **分阶段呈现**：先返回 folders + 简单 count（若已有冗余字段或轻量查询），首屏只渲染文件夹树/列表；再在客户端或 RSC 流式请求“每个文件夹的详细统计”和“最近书签”。
2. **RPC 与查询优化**：为 `get_folder_bookmark_stats` 加索引、限制 folder_ids 数量或分页；recentBookmarks 限制条数并确保有索引。
3. **缓存**：对 folders 列表和统计做短时 cache（如 `unstable_cache` 或 CDN），避免每次进入都全量重算。

**验收**

- Folders 页 TTFB 明显下降；大账号下仍可接受。

### 3.4 Search 页

**问题**

- 有 `q` 时在服务端做全文/语义搜索，大结果集或复杂查询会拖慢首屏。

**建议**

- 保留“服务端首屏结果”的前提下，限制首屏条数（如 20），并做好 loading 态；更多结果交给客户端分页或“加载更多”。
- 确保搜索 API 有索引、限流和超时，避免单次请求过长。

## 四、P0：Context 与重渲染

### 4.1 HomeView 订阅过多

**问题**

- `HomeView` 同时使用：`useHomePageContext`、`useHomeData`、`useHomeViewMode`、`useDialogs`、`useSelectionMode`、`useClassificationPolling`、`useSynthesisRecommend` 等。
- 任一 Context 更新都会导致 HomeView 整树重渲染，进而把整棵列表树推倒重算（即使用虚拟列表，上层组件仍会执行）。

**建议**

1. **按需取用、拆子组件**：
   - 把“仅用 filter”的部分拆成只订阅 `useFilter()` 的子组件；
   - “仅用 viewMode”的拆成只订阅 `useViewMode()`；
   - 列表区域单独成组件，只接收 `bookmarks`、`hasMore`、`onLoadMore` 和稳定的回调（见下），避免依赖整个 HomeView 的 Context。
2. **稳定回调**：
   - 所有传给列表/卡片的反调（onEdit、onDelete、onLoadMore、onToggleSelect 等）在父级用 `useCallback` 绑定稳定依赖，确保 Virtual 列表和 BookmarkCard 的 memo 生效。
3. **HomePageContext 取值方式**：
   - 若当前仍从 `useHomePageContext()` 拿“大对象”，改为在具体子组件里只消费需要的细粒度 Context（如 `useFilter()`、`useViewMode()`），减少因“大对象引用变化”导致的重渲染。

**验收**

- 切换 platform/folder、排序、视图模式时，React DevTools 中 HomeView 及列表子树的渲染次数明显减少；滚动、筛选时无明显卡顿。

### 4.2 AppHeader 与全局 Context

**问题**

- AppHeader 使用 `useUser`、`useHomePageSafe`、`useSearchParams`、`usePathname` 等，路由或搜索参数变化会触发重渲染；若 Header 较重，会拖累全站体感。

**建议**

- Header 内按区域拆成小组件（如：Logo/导航、搜索/筛选、用户菜单），每个只订阅自己需要的 Context/路由。
- 对“仅用于展示”的数据，考虑用 `useSyncExternalStore` 或 selector 形态的订阅，避免整块 Context 变更就重绘整块 Header。

### 4.3 列表层：Virtuoso 与回调稳定性

**问题**

- `VirtualBookmarkGrid` 的 `itemContent={(index, bookmark) => (...)}` 每次父组件渲染都是新函数，可能导致 Virtuoso 内部认为 props 变化而做多余 diff 或子组件更新。
- 若 `onEdit`/`onDelete`/`onToggleSelect` 等未用 `useCallback`，BookmarkCard 的 memo 会失效，列表项会大量重渲染。

**建议**

1. **itemContent**：
   - 将 `itemContent` 改为使用 `useCallback` 或 `useMemo` 生成的稳定函数，内部根据 `index`/`bookmark` 渲染；或把单条渲染拆成独立组件，在组件内用 memo + 稳定 props。
2. **列表父组件**：
   - 在 `HomeContent`/负责传 props 的父级，对所有传给 Virtual 列表和 BookmarkCard 的回调使用 `useCallback`，依赖项仅包含必要状态（如 setState、id 等）。
3. **selectedIds**：
   - 若 `selectedIds` 是 Set，确保用同一引用或通过“选中 id 列表”的稳定比较（如只传 `selectedIds.has(id)` 的 boolean）避免因 Set 引用变化导致整列表更新；必要时用 ref 存 Set，通过 forceUpdate 或细粒度订阅只更新受影响的项。

**验收**

- 滚动时仅可见区域内的卡片参与渲染；选中/取消选中时仅受影响项重渲染。

## 五、P1：列表与虚拟滚动

### 5.1 虚拟列表 overscan 与高度

**问题**

- `overscan={200}` 在 react-virtuoso 中多为像素；过大可能多渲染很多行，过小会滚动时频繁挂载/卸载造成抖动。
- 若未设置合适 `listClassName`/行高或 `increaseViewportBy`，在复杂卡片高度下可能出现跳动或重复测量。

**建议**

- 根据实际卡片高度设定合理 overscan（如 1–2 屏高度对应的像素），避免 200px 过大。
- 列表模式若行高固定，使用固定 `itemSize`（若 Virtuoso 支持）或 `increaseViewportBy` 优化；网格模式确认 `components.List` 的 grid 行高与 CSS 一致，减少 layout thrashing。

### 5.2 BookmarkCard 单卡成本

**问题**

- BookmarkCard 内部依赖多（formatRelativeTime、平台色、placeholder、TTS、Snapshot、Dropdown 等），单卡渲染成本不低；在虚拟列表下虽只渲染可见项，但单卡过重仍会拉高帧时间。

**建议**

- 用 React DevTools Profiler 抓一次“滚动 + 筛选”的火焰图，确认单卡 render 时间。
- 将卡片内“非首屏必需”的部分（如 TTS、Snapshot 菜单、复杂 Tooltip）改为懒加载或按需渲染（如 hover 再挂载）。
- 确保卡片内部子组件也按需 memo，避免父级更新导致整卡重算。

### 5.3 加载更多

**问题**

- `loadMore` 通过 `appendToCache` 更新 SWR 的数组状态，会触发整列表 re-render；若列表根组件未做稳定性优化，可能整树更新。

**建议**

- 列表容器和 Virtuoso 只接收 `bookmarks` 和稳定回调；`appendToCache` 后由 SWR 更新，通过 4.1/4.3 的拆分和稳定引用，确保只有列表和新增项参与更新，而不是整页重渲染。
- 若 Virtuoso 支持“追加数据不重置滚动”，确认使用正确 API，避免“加载更多”时列表跳动或回到顶部。

## 六、P2：轮询与后台刷新

### 6.1 useProcessingPoller / useClassificationPolling

**问题**

- Processing 轮询每 3s 一次，有 PROCESSING 书签时会 `mutate` 列表；分类轮询也会触发状态更新。若列表未做细粒度更新，每次轮询都会带来整列表重绘。

**建议**

- 轮询结果更新时，尽量只更新“变化的那一条”书签（例如通过 `updateCacheItem(id, updater)`），避免整列表 `setData([...])`。
- 确认 useBookmarksSWR 的 `updateCacheItem` 实现不会导致整数组引用变化（如用 immutable update 只改对应项）。
- 页面不可见时已暂停轮询，保持即可；可见时恢复间隔可适当拉长（如 5s）以降低主线程占用。

### 6.2 其他 refetchInterval

**问题**

- notification-count、inbox-counts、organize-counts 等存在 refetchInterval，会周期触发请求和 Context/状态更新，可能间接触发整页或 Header 重渲染。

**建议**

- 将“数量角标”等从主列表/首页 Context 中拆出，单独组件 + 单独的小 Context 或 SWR key，避免数量更新触发首页大子树。
- 适当提高 refetchInterval（如 60s→120s）或改为“窗口 focus 时 revalidate”，减少后台常驻请求。

## 七、P2：布局与动画

### 7.1 willChange 与 transition

**问题**

- `MainContentWrapper` 使用 `willChange: "margin-left"` 且长期存在，会促使浏览器为该区域单独开层；侧栏折叠动画结束后若不移除，可能增加 compositing 成本。
- `transition-[margin-left] duration-200` 在低端设备上可能带来主线程重排。

**建议**

- 侧栏展开/折叠动画进行中时再设置 `willChange: "margin-left"`，动画结束（transitionend 或 200ms 后）移除。
- 若移动端无侧栏，该区域不必加 `willChange`。

### 7.2 Suspense 与骨架屏

**问题**

- 多处 lazy + Suspense 在 resolve 时依次替换 fallback，可能造成布局多次跳动（如工具栏、列表骨架、对话框占位）。

**建议**

- 骨架屏与真实内容的占位尺寸尽量一致（如固定高度、固定网格列数）。
- 对“非首屏关键”的 lazy 块使用 `fallback={null}` 或极小占位，避免大面积布局偏移；首屏关键块（如列表）保留骨架，但保证骨架与最终列表的布局一致。

| 阶段 | 内容                                                 | 预期效果                 |
| ---- | ---------------------------------------------------- | ------------------------ |
| 1    | 首页 RSC 并行请求 + 减少重复请求（3.1、3.2）         | 首屏 TTFB/LCP 下降       |
| 2    | HomeView 拆子组件 + 稳定回调（4.1、4.3）             | 筛选/排序/视图切换不卡   |
| 3    | Virtuoso itemContent 与列表 props 稳定化（4.3、5.1） | 滚动更顺、memo 生效      |

## 九、度量与验收

- **首屏**：LCP、TTFB、FCP（可沿用现有 Web Vitals）。
- **交互**：筛选/排序/切换视图后到列表稳定的时间；滚动 FPS（Chrome Performance 或 React Profiler）。
- **内存**：长时间使用后虚拟列表与 SWR 缓存是否增长异常。

建议在关键路径加少量 `performance.mark`/`measure`（如“home-data-ready”“first-list-paint”），便于对比优化前后。

---

## 十、风险与注意

- 放宽 `dynamic` 或加缓存时，需保证“登录态/多端一致性”仍正确（例如不缓存用户级数据到 CDN）。
- Context 拆分后要确认所有使用 `useHomePageContext` 的地方已迁移到细粒度 Hook，避免漏改导致功能异常。
- 虚拟列表与“加载更多”的交互要回归：滚动位置、选中态、键盘/无障碍焦点不丢失。

以上方案供评审与排期使用；实施时可按 P0→P1→P2 分迭代推进，每步做小范围验证再推广。
