## 三、架构问题与风险 ⚠️

### P0 - 严重问题

| 问题                    | 影响                   | 现状                       |
| ----------------------- | ---------------------- | -------------------------- |
| **lib/ 模块过于庞大**   | 职责边界模糊，难以维护 | 193 个文件，占 src/ 的 42% |
| **分类系统 V3/V4 共存** | 代码冗余，认知负担高   | 106 个文件，多版本并行     |
| **循环依赖风险**        | 构建不稳定，测试困难   | lib/ 内部模块交叉引用      |

### P1 - 中等问题

| 问题                  | 影响                   | 现状                       |
| --------------------- | ---------------------- | -------------------------- |
| **API 路由过多**      | 维护成本高，缺乏聚合层 | 98 个路由，部分功能重叠    |
| **Hooks 缺乏分层**    | 业务逻辑与 UI 耦合     | 32 个 hooks 平铺在同一目录 |
| **缺少 API 版本控制** | 破坏性变更难以管理     | 无 /v1/, /v2/ 命名空间     |
| **测试覆盖不足**      | 回归风险高             | 仅分类系统有测试           |

### P2 - 次要问题

| 问题              | 影响         | 现状                     |
| ----------------- | ------------ | ------------------------ |
| **文档分散**      | 新人上手困难 | 根目录大量中文 md 文件   |
| **Magic Numbers** | 可读性差     | 阈值硬编码在代码中       |
| **日志不统一**    | 问题排查困难 | console.log 与 pino 混用 |

## 四、优化建议（按优先级）

### 🔴 P0：模块重组（建议立即执行）

**问题**：`lib/` 目录承载了过多职责，导致模块边界模糊

**建议方案**：采用**特性切片架构 (Feature-Sliced Design)**

```
src/
├── app/                      # Next.js 路由（保持不变）
├── shared/                   # 共享基础设施
│   ├── ui/                   # 基础 UI 组件（从 components/ui 移入）
│   ├── lib/                  # 纯工具函数（无业务逻辑）
│   │   ├── utils/
│   │   ├── cache/
│   │   └── logger/
│   ├── hooks/                # 通用 hooks（use-debounce, use-media-query）
│   └── types/                # 全局类型定义
│
├── features/                 # 业务特性模块（核心重构点）
│   ├── classification/       # 分类系统（整合 V4）
│   │   ├── api/              # API 路由
│   │   ├── components/       # 分类相关组件
│   │   ├── hooks/            # 分类专用 hooks
│   │   ├── services/         # 核心服务
│   │   └── types/            # 分类类型
│   │
│   ├── bookmarks/            # 书签管理
│   │   ├── api/
│   │   ├── components/
│   │   ├── hooks/
│   │   └── services/
│   │
│   ├── folders/              # 文件夹管理
│   ├── import/               # 导入功能
│   ├── messages/             # 消息系统
│   └── search/               # 搜索功能
│
├── entities/                 # 业务实体（跨特性复用）
│   ├── bookmark/
│   ├── folder/
│   └── user/
│
└── widgets/                  # 组合组件（页面级别）
    ├── sidebar/
    ├── header/
    └── bookmark-list/
```

**迁移步骤**：

1. 创建 `features/` 目录结构
2. 将分类系统整合为 `features/classification/`（删除 V3，保留 V4）
3. 配置路径别名：`@/features/*`, `@/shared/*`, `@/entities/*`
4. 逐步迁移，保持 CI 通过

### 🟠 P1：API 层优化

**问题**：98 个 API 路由，部分功能重叠，缺乏聚合

**建议方案**：引入**服务聚合层 + API 版本控制**

```typescript
// 1. 创建聚合服务层
// src/features/bookmarks/services/bookmark-facade.ts
export class BookmarkFacade {
  constructor(
    private bookmarkService: BookmarkService,
    private classificationService: ClassificationService,
    private embeddingService: EmbeddingService,
  ) {}

  // 聚合操作：保存 + 分类 + 生成嵌入
  async saveWithClassification(input: BookmarkInput): Promise<BookmarkResult> {
    const bookmark = await this.bookmarkService.create(input);
    const classification = await this.classificationService.classify(bookmark);
    const embedding = await this.embeddingService.generate(bookmark);
    return { bookmark, classification, embedding };
  }
}

// 2. API 版本控制
// src/app/api/v1/bookmarks/route.ts
// src/app/api/v2/bookmarks/route.ts（未来版本）
```

**路由精简建议**：

| 当前                                 | 建议                      | 说明                             |
| ------------------------------------ | ------------------------- | -------------------------------- |
| `/api/classification/classify`       | 合并                      | ↓                                |
| `/api/classification/classify-deep`  | `/api/v1/classification`  | 通过参数 `mode=quick\|deep` 区分 |
| `/api/classification/classify-quick` | 合并                      | ↑                                |
| `/api/bookmarks/batch-delete`        | 合并                      | ↓                                |
| `/api/bookmarks/batch-move`          | `/api/v1/bookmarks/batch` | 通过 `action` 字段区分           |
| `/api/bookmarks/batch-restore`       | 合并                      | ↑                                |

### 🟡 P2：日志统一

**问题**：`console.log` 与 `pino` 混用

**建议方案**：**统一使用结构化日志**

```typescript
// src/shared/lib/logger/index.ts
import pino from "pino";

export const logger = pino({
  level: process.env.LOG_LEVEL || "info",
  formatters: {
    level: (label) => ({ level: label }),
  },
});

// 创建带上下文的子 logger
export const createLogger = (module: string) => logger.child({ module });

// 使用
const classificationLogger = createLogger("classification");
classificationLogger.info({ bookmarkId, folderId }, "Classified bookmark");
```

### 🟡 P2：测试覆盖提升

**问题**：仅分类系统有测试，其他模块缺失

**建议方案**：**分层测试策略**

```
测试金字塔：
          /\
         /  \
        / E2E \        (10%) Playwright - 关键用户流程
       /________\
      /          \
     / Integration \ (30%) API 路由 + 数据库交互
    /______________\
   /                \
  /    Unit Tests    \ (60%) Services + Utils + Hooks
 /____________________\
```

**优先级建议**：

1. **API 路由测试** - 核心 CRUD 操作
2. **分类服务测试** - 已有，扩充边界情况
3. **Hook 测试** - 使用 @testing-library/react-hooks
4. **E2E 测试** - 书签保存 → 分类 → 搜索流程
