## 二、架构优势

### 2.1 清晰的分层结构

```
src/
├── app/           # Next.js App Router (路由层)
├── components/    # UI 组件层
├── contexts/      # 全局状态层
├── hooks/         # 逻辑复用层
├── lib/           # 工具/服务层
├── types/         # 类型定义层
└── features/      # 功能模块层 (新增)
```

**评分: 8/10** - 层次清晰，职责分明

### 2.2 成熟的缓存系统

`src/lib/cache/` 模块设计优秀：

```typescript
// 统一导出，API 清晰
export { useBookmarksSWR } from "./hooks/use-bookmarks-swr";
export { KeepAliveProvider, KeepAliveOutlet } from "./keep-alive";
export { cachePerformanceTracker } from "./cache-performance-tracker";
```

**包含功能**:

- ✅ SWR 数据缓存
- ✅ KeepAlive 页面缓存
- ✅ 性能追踪器
- ✅ 自动失效策略

**评分: 9/10** - 生产级缓存方案

### 2.3 客户端导航优化

`NavigationContext` + `KeepAlive` 组合实现 SPA 级体验：

- URL 同步无服务端导航
- 页面状态保持
- 预加载支持

**评分: 8.5/10** - 性能与体验平衡良好

### 2.4 首页重构成功 (Phase 3)

Context-first 模式迁移完成：

| 指标          | 优化前   | 优化后   | 提升      |
| ------------- | -------- | -------- | --------- |
| 代码行数      | ~1200行  | ~560行   | 53% ↓     |
| Window Events | 12+ 个   | 2 个     | 83% ↓     |
| API 调用      | 重复调用 | 单次调用 | 100% 修复 |
| FCP           | ~800ms   | 556ms    | 30% ↓     |

**评分: 9/10** - 重构目标达成

## 三、架构问题

### 3.1 【严重】Hooks 数量失控

**现状**: 44 个自定义 Hook，缺乏分类和组织

```
hooks/
├── use-bookmark-actions.ts      # 业务逻辑
├── use-debounce.ts              # 通用工具
├── use-local-storage.ts         # 通用工具
├── use-media-query.ts           # UI 相关
├── use-custom-usage-tags.ts     # 业务逻辑
├── use-import-session.ts        # 业务逻辑
├── ... 38 more files
```

**问题**:

- 难以发现和复用
- 命名不一致
- 部分功能重复
- 缺乏文档

**建议**: 按职责分类为 `core/`, `domain/`, `ui/`

**严重程度**: ⚠️ P1

### 3.2 【严重】lib/ 目录膨胀

**现状**: 30+ 个模块，职责混乱

```
lib/
├── cache/              # ✅ 独立系统
├── classification/     # ✅ 独立系统
├── browser-bookmark/   # ✅ 独立系统
├── utils.ts            # ❌ 杂货铺
├── supabase/           # ✅ 基础设施
├── constants/          # ❌ 应该在 config/
├── url-utils.ts        # ❌ 应该在 utils/
├── date-utils.ts       # ❌ 应该在 utils/
└── ... 20+ more
```

**问题**:

- `utils.ts` 成为"万能抽屉"
- 分散的工具函数难以维护
- 常量配置混乱

**建议**: 采用 Feature-Sliced Design 重组

**严重程度**: ⚠️ P1

### 3.3 【中等】API 路由过度嵌套

**现状**:

```
api/
├── bookmarks/
│   ├── [id]/
│   │   ├── route.ts
│   │   ├── summary/route.ts
│   │   └── tags/route.ts
│   ├── batch/route.ts
│   └── search/route.ts
├── browser-bookmark/
│   ├── folders/route.ts
│   ├── import/route.ts
│   └── ...
└── ... 更多嵌套
```

**问题**:

- 嵌套层级过深 (最深 4 层)
- 路由发现困难
- 缺乏版本控制

**建议**: 引入 API 版本化 `/api/v1/`

**严重程度**: ⚠️ P2

### 3.4 【中等】组件目录碎片化

**现状**: 32 个组件子目录

```
components/
├── analytics/          # 2 文件
├── bookmark/           # 12 文件
├── browser-bookmark/   # 8 文件
├── home/               # 6 文件
├── layout/             # 5 文件
├── pwa/                # 2 文件
├── ui/                 # 30+ 文件 (Shadcn)
└── ... 25 more directories
```

**问题**:

- 小目录过多 (2-3 文件的目录)
- 组件归属不清晰
- 跨目录依赖复杂

**建议**: 合并相关目录，按功能域组织

**严重程度**: ⚠️ P2

### 3.5 【低】types/ 目录混乱

**现状**:

```
types/
├── index.ts
├── supabase.ts
├── database.types.ts
├── database.types.ts.bak    # ❌ 备份文件
├── database.types.ts.bak2   # ❌ 备份文件
└── ... 更多备份
```

**问题**:

- 存在多个 `.bak` 备份文件
- 应使用 Git 管理版本

**建议**: 清理备份文件，统一类型导出

**严重程度**: ⚠️ P0 (快速修复)
