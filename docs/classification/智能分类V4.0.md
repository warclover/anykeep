# 智能分类 V4.0 整体架构与演进计划

**文档版本**：V4.0-Final
**日期**：2025-12-08
**来源**：基于 [V3.0 代码审计] 与 [V3.5 深度优化方案] 整合制定
**目标**：将智能分类从"功能模块"升级为"工业级智能子系统"，实现**透明化、自进化、零感知延迟**。

---

## 一、 核心愿景与设计哲学

V4.0 不再仅仅追求分类的准确率，而是重新定义用户与 AI 的协作关系：

1.  **从黑盒到白盒 (Transparency)**：用户不再只是被动接受结果，而是能看到 AI 的决策路径（Traceability）和对文件夹的理解（Profile Visualization）。
2.  **从静态到动态 (Self-Evolution)**：系统不再使用硬编码权重，而是根据用户行为实时调整策略（Dynamic Weights）和配置（DB Config）。
3.  **从等待到即时 (Zero-Latency)**：通过乐观 UI 和端侧预测，将用户感知延迟降至 0ms。

---

| :----------- | :------------- | :----------------------------------------------------------------------------------- | :--------- |
| **检索层**   | 向量+标签+指纹 | **语义重排序 (Re-ranking)**<br>引入轻量级模型对召回结果二次打分，去除噪音。          | 准确率 ↑   |
| **决策层**   | CoT Prompt     | **决策透明化**<br>前端展示："已归入[前端]，因为：1.包含React标签 2.与历史收藏相似"。 | 用户信任 ↑ |
| **自动创建** | 规则驱动       | **风格化命名引擎**<br>Few-Shot 学习用户的命名习惯（如 "Tech/..."），拒绝机器味。     | 体验 ↑     |

### 3.3 交互与反馈：极速与闭环

| 模块         | V3.0 现状       | V4.0 演进方案                                                                             | 价值         |
| :----------- | :-------------- | :---------------------------------------------------------------------------------------- | :----------- |
| **响应速度** | 1-2秒 (等待 AI) | **乐观 UI (Optimistic UI)**<br>前端先假定 Tier 1 结果正确，后台静默校验，错误再推送修正。 | 感知延迟 0ms |

### 3.4 LLM 选型与调度策略 (New)

结合项目现有资源（阿里百炼云/DeepSeek），采用混合调度策略：

| 场景                                    | 推荐模型            | 理由                                                         |
| :-------------------------------------- | :------------------ | :----------------------------------------------------------- |
| **主力 (Tier 2)**<br>CoT 推理、重排序   | **DeepSeek-V3**     | 推理能力 Top Tier，JSON 遵循度高，且成本极低，适合高频调用。 |
| **专家 (Tier 3)**<br>命名优化、自动创建 | **Qwen-Max (阿里)** | 中文语感极佳，能生成"信达雅"的文件夹名称，避免机器味。       |
| **深思 (Librarian)**<br>整理大师巡检    | **DeepSeek-R1**     | 具备深度推理能力，适合处理全库结构分析这种复杂的逻辑任务。   |

## 四、 实施路线图 (Roadmap)

我们将升级计划分为三个阶段，每阶段 2 周。

### Phase 1: 稳基座与高性能 (Stability & Performance)

**目标**：解决系统复杂度问题，降低响应延迟。

1.  **数据库优化**：将 Postgres 向量索引迁移至 `HNSW`，查询速度提升 10 倍。
2.  **全链路追踪**：实现 `TraceID` 和调试面板，记录每个匹配器的得分详情。
3.  **配置中心化**：将 `UNIVERSAL_CATEGORIES` 和 `WEIGHTS` 迁移至 Supabase 数据库。
4.  **实时纠错**：实现 Feedback 立即写入 Redis/内存缓存的逻辑。

### Phase 2: 强交互与透明化 (Experience & Transparency)

**目标**：让用户"看见" AI 的思考，提升信任度。

1.  **乐观 UI 改造**：重构前端状态管理，支持"先展示，后校验"的流式交互。
2.  **决策理由透传**：后端 API 返回简化的决策原因，前端在 Toast/卡片中展示。
3.  **文件夹画像可视化**：在文件夹详情页开发"AI 理解面板"（词云/特征标签）。

### Phase 3: 自进化与多模态 (Evolution & Intelligence)

**目标**：系统具备自我优化的能力，并扩展内容理解边界。

1.  **动态权重引擎**：实现基于用户画像（冷启动/资深）自动切换权重配置的逻辑。
2.  **整理大师主动巡检**：开发后台定时任务，扫描异常文件夹结构并生成通知。
3.  **多模态预研**：接入视觉模型，尝试对图片/视频封面进行分类（为 V4.1 做准备）。

## 六、 风险评估与应对

1.  **幻觉风险**：乐观 UI 先展示了分类，但后台 AI 判定错误。
    - _应对_：前端设计优雅的"修正动画"，并提示"AI 已根据您的最新习惯自动修正"。
2.  **成本风险**：主动巡检可能消耗大量 Token。
    - _应对_：限制巡检频率（周更），且仅对活跃用户开启；优先使用轻量级模型。
3.  **数据一致性**：配置热更新可能导致短时间内的服务节点状态不一致。
    - _应对_：接受短时间（分钟级）的最终一致性，配置更新主要影响新请求。
