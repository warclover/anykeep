# AnyKeep 精简方案：专职收藏整理智能体

> 目标：将 AnyKeep 从"全能 AI 知识管理平台"精简为"专职收藏整理智能体"
> 原则：YAGNI + KISS — 只保留「收藏整理」核心链路上的功能

---

## 一、精简总览

| 维度           | 当前      | 精简后   | 削减比例 |
| -------------- | --------- | -------- | -------- |
| AI Skills      | 30 个     | 8 个     | -73%     |
| AI Tools       | 127 个    | ~40 个   | -69%     |
| 分类策略       | 130+ 文件 | ~30 文件 | -77%     |
| Cron Jobs      | 16 个     | 5 个     | -69%     |
| Edge Functions | 12 个     | 5 个     | -58%     |
| API 路由       | 200+ 个   | ~80 个   | -60%     |
| Feature Flags  | 86 个     | ~15 个   | -83%     |
| UI 组件目录    | 40+ 个    | ~20 个   | -50%     |

### 分类版本策略

```
当前：V4.1 + V5.0 并存 + V5.5 晶体 + V3 兼容层
精简后：仅保留 V4.1（SimpleClassificationService）
```

**理由**：V4.1 已在生产中验证稳定，对于「收藏整理」场景足够。V5.0 的 L0/T0/T1 三层管道、LLM 深度集成带来的边际收益不足以覆盖其复杂度成本。

## 十一、精简执行策略建议

### 不建议直接删除代码

推荐采用 **Feature Flag 关闭 + 渐进式移除** 的策略：

**Phase 1（1-2 周）：Flag 关闭**

1. 将所有要移除的 Skills 通过 Feature Flag 关闭
2. 将不需要的 Cron Jobs 停止调度
3. UI 上隐藏不需要的页面入口（路由保留但不展示）

**Phase 2（2-4 周）：代码隔离**

1. 将要移除的模块移到 `src/_deprecated/` 目录
2. 确认没有运行时依赖后再物理删除
3. 逐步清理 API 路由

**Phase 3（4-6 周）：物理删除**

1. 确认系统稳定运行后，删除 `_deprecated` 目录
2. 清理无用的数据库迁移
3. 清理无用的类型定义

### 风险控制

| 风险                     | 缓解措施                                 |
| ------------------------ | ---------------------------------------- |
| 移除模块有隐藏依赖       | Phase 1 仅 Flag 关闭，不删代码，观察运行 |
| 用户依赖被移除的功能     | 产品层面提前通知，提供数据导出           |
| 精简后发现某功能需要回归 | `_deprecated` 目录保留 4 周，随时可恢复  |
| 分类准确率下降           | V4.1 已在生产验证，预期无影响            |

## 附：精简后保留的核心用户旅程

1. **添加收藏** → crawl-content 提取元数据 → generate-ai-content 生成标签 → classify-bookmark 自动分类
2. **查看收件箱** → inbox_triage 聚类分析 → 用户确认或 Agent 自动处理
3. **整理收藏** → batch_organize 批量整理 → duplicate_cleanup 去重
4. **搜索收藏** → search 语义搜索 → 返回结果
5. **管理文件夹** → folder_recommend 推荐 → folder_health_check 健康检查
6. **导入书签** → import-browser-bookmarks → 批量分类

以上 6 条链路覆盖了「收藏整理智能体」的核心价值。
