# 🔍 AnyKeep 消息系统 CTO 评审报告

> 评审日期：2025-12-10
> 评审人：AI CTO

## 一、系统总览

消息系统整体设计较为完善，包含 **27 种消息类型**、**3 级分级制度**、完整的数据库函数和 API 路由。但在深入审查后，发现以下几类问题：

---

## 二、🔴 关键逻辑问题

### 问题 1：消息分发机制断裂

**位置**：`src/lib/messages/message-dispatcher.ts:70-82`

```typescript
static dispatchFromResult(result: MessageResult): void {
  if (!result.success || !result.title) {
    return;  // 静默失败，无日志
  }
  // ...
}
```

**问题**：

- 服务端创建消息后返回 `MessageResult`，但前端需要**主动调用** `dispatchFromResult`
- 当前代码库中，**多数业务调用点没有处理返回值**，导致 Toast/Modal 从未被触发

**影响**：用户操作后看不到即时反馈

---

### 问题 2：Modal Handler 注册时机不确定

**位置**：`src/lib/messages/message-dispatcher.ts:60-63`

```typescript
if (config.showModal && this.modalHandler) {
  this.modalHandler(message as Message);
}
```

**问题**：

- `modalHandler` 需要在根组件注册，但如果用户直接访问某个页面，handler 可能尚未注册
- 静态类的状态在 SSR/CSR 切换时可能丢失

---

### 问题 3：分页合并逻辑存在 Bug

**位置**：`src/hooks/use-messages.ts:264-289`

```typescript
function mergeGroups(
  existing: MessageGroup[],
  newGroups: MessageGroup[],
): MessageGroup[] {
  // 简单追加，未处理时间顺序
  result[existingIndex].messages.push(...uniqueNewMessages);
  // ...
}
```

**问题**：

- 加载更多时，新消息直接追加到分组末尾，**破坏了时间排序**
- 例如：第一页最后一条是"今天 10:00"，第二页第一条是"今天 09:00"，合并后顺序错乱

---

### 问题 4：未读数统计与用户偏好脱节

**位置**：数据库函数 `get_unread_message_counts`

**问题**：

- 统计了所有未读数（包括 silent 级别）
- 但用户可能已在 `notification_preferences` 中关闭了某些级别的提醒
- 角标显示的未读数与用户实际能感知的不一致

---

### 问题 5：批量标记已读的竞态条件

**位置**：`src/hooks/use-messages.ts:200-215`

```typescript
const markAllAsRead = useCallback(async (): Promise<boolean> => {
  const response = await fetch("/api/messages/batch-read", { ... });
  if (response.ok) {
    await mutate();  // 简单刷新
  }
}, [mutate]);
```

**问题**：

- 用户点击"全部已读"后，新消息可能同时到达
- 刷新时可能把新消息的 UI 状态也标记为已读（视觉上）

---

## 三、🟠 架构设计问题

### 问题 6：服务端消息创建缺少实时推送

**现状**：

```
服务端 → 数据库 → 客户端轮询/手动刷新 → 显示
```

**问题**：

- 没有 WebSocket/SSE 实时推送
- 用户必须刷新页面或等待轮询才能看到新消息
- 重要消息（如系统公告）无法即时触达

---

### 问题 7：消息等级与优先级定义冗余

**位置**：`src/lib/messages/message-levels.ts`

存在两套优先级系统：

1. `level`: `silent | normal | important` - 决定展示行为
2. `priority`: 1-10 - 存储在数据库中

**问题**：

- `priority` 字段几乎未被使用（仅写入，未读取排序）
- 两套系统增加理解成本

---

### 问题 8：消息模板硬编码

**位置**：`src/lib/messages/message-templates.ts`

所有模板硬编码在 TypeScript 中：

- 新增/修改消息类型需要**重新部署**
- 多语言支持困难
- A/B 测试文案不灵活

---

## 四、🟡 性能问题

### 问题 9：API 路由双次查询

**位置**：`src/app/api/messages/route.ts:70-106`

```typescript
// 第一次查询：获取消息列表
const { data: messages } = await supabase.rpc("get_messages_grouped", ...);

// 第二次查询：获取总数
const { data: totalResult } = await supabase.rpc("get_messages_count", ...);
```

**问题**：

- 每次请求都执行两次数据库调用
- 可以合并为单次查询返回 `{messages, total}`

---

### 问题 10：SWR 缓存策略过于激进

**位置**：`src/hooks/use-messages.ts:121-128`

```typescript
const { data, error, isLoading, mutate } = useSWR<GetMessagesResponse>(
  buildUrl(page),
  fetcher,
  {
    refreshInterval, // 可能被设为0或很大的值
    revalidateOnFocus: false, // 切换tab不刷新
  },
);
```

**问题**：

- 用户长时间停留在消息页，数据可能过时
- 未读数角标与实际列表不同步

---

## 五、🔵 用户体验问题

### 问题 11：消息操作缺少乐观更新

当前流程：

```
用户点击删除 → 等待 API 响应 → 刷新列表 → UI 更新
```

**问题**：操作延迟明显（500ms-2s），用户感知卡顿

**建议**：使用乐观更新 + 回滚机制

---

### 问题 12：空状态处理不完善

**位置**：`src/components/messages/message-empty-state.tsx`

- 只有一种空状态
- 未区分"从未有消息"和"已全部处理完"

---

### 问题 13：重要消息 Modal 缺少关闭后处理

**位置**：`src/components/messages/message-modal.tsx`

- 用户关闭 Modal 后，消息仍为未读状态
- 下次打开应用可能再次弹出相同消息

### 方案 B：改进前端分发流程

```typescript
// hooks/use-message-notification.ts
export function useMessageNotification() {
  const { refresh: refreshList } = useMessages();
  const { refresh: refreshCount } = useUnreadCount();

  const dispatch = useCallback(async (result: MessageResult) => {
    if (!result.success) return;

    // 1. 即时 Toast/Modal
    MessageDispatcher.dispatchFromResult(result);

    // 2. 刷新未读数（去抖）
    debouncedRefreshCount();

    // 3. 如果在消息页，刷新列表
    if (isOnMessagesPage()) {
      await refreshList();
    }
  }, []);

  return { dispatch };
}
```

## 八、总结

| 维度       | 评分     | 说明                   |
| ---------- | -------- | ---------------------- |
| 功能完整性 | ⭐⭐⭐⭐ | 27种消息类型覆盖全面   |
| 代码质量   | ⭐⭐⭐⭐ | 类型安全、模块化较好   |
