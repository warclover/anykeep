## 2. 架构设计：三端统一策略

### 2.1 核心原则：**"一次开发，三端运行"**

```
┌─────────────────────────────────────────┐
│        共享业务逻辑层 (Shared)           │
│  - API 调用 (Supabase Client)          │
│  - 数据模型 (TypeScript Types)          │
│  - 工具函数 (Utils)                     │
│  - AI 服务 (DeepSeek, Qwen-VL)         │
└─────────────────────────────────────────┘
           ↓        ↓        ↓
    ┌──────────┐ ┌──────────┐ ┌──────────┐
    │   Web    │ │   App    │ │  小程序  │
    │ (Next.js)│ │(Capacitor)│ │ (Taro)  │
    └──────────┘ └──────────┘ └──────────┘
```

### 2.2 目录结构建议

```
anykeep/
├── src/                    # Web 端代码（现有）
│   ├── app/
│   ├── components/
│   └── lib/
├── mobile/                # App 端代码（Capacitor）
│   ├── app/                 # 复用 Web 的 app 目录
│   ├── components/          # 复用 Web 的 components
│   └── lib/                 # 复用 Web 的 lib
│   └── native/              # 原生能力封装（已有 capacitor.ts）
├── miniprogram/             # 小程序端代码（Taro）
│   ├── src/
│   │   ├── pages/          # 页面（对应 Web 的 app 路由）
│   │   ├── components/     # 组件（复用 Web 组件，需适配）
│   │   └── services/       # API 服务（复用 Web 的 lib）
│   └── config/             # 小程序配置
└── shared/                  # 共享代码（新增）
    ├── types/              # TypeScript 类型定义
    ├── api/                # API 客户端（Supabase）
    ├── utils/              # 工具函数
    └── constants/          # 常量定义
```

## 3. 小程序方案：Taro 框架

### 3.1 为什么选择 Taro？

**优势**：

- ✅ **React 语法**：与现有 Next.js 代码高度一致，复用率 80%+
- ✅ **多端支持**：一套代码同时支持微信、支付宝、抖音小程序
- ✅ **类型安全**：完整的 TypeScript 支持
- ✅ **生态成熟**：社区活跃，文档完善

**对比其他方案**：

- ❌ **原生小程序**：需要重写所有代码，成本高
- ❌ **uni-app**：Vue 语法，与现有 React 代码不兼容
- ❌ **Remax**：已停止维护

**1. 初始化 Taro 项目**

## 5. 关键技术难点与解决方案

### 5.1 数据同步策略

**问题**：三端数据如何保持一致？

**方案**：**Supabase Realtime + 乐观更新**

```typescript
// shared/api/bookmarks.ts
import { createClient } from "@supabase/supabase-js";

export function subscribeToBookmarks(
  userId: string,
  callback: (bookmark: Bookmark) => void,
) {
  const supabase = createClient(SUPABASE_URL, SUPABASE_ANON_KEY);

  // 实时监听书签变化
  supabase
    .channel("bookmarks")
    .on(
      "postgres_changes",
      {
        event: "*",
        schema: "public",
        table: "bookmarks",
        filter: `user_id=eq.${userId}`,
      },
      (payload) => {
        callback(payload.new as Bookmark);
      },
    )
    .subscribe();
}
```

### 5.2 图片处理与存储

**问题**：小程序和 App 的图片上传、压缩策略不同。

**方案**：**统一使用 Supabase Storage**

```typescript
// shared/utils/image-upload.ts
export async function uploadImage(
  file: File | string,
  platform: "web" | "app" | "miniprogram",
) {
  // Web: File 对象
  // App: Capacitor Filesystem API
  // 小程序: Taro.chooseImage 返回的路径

  const formData = new FormData();
  // 统一转换为 FormData

  const { data, error } = await supabase.storage
    .from("bookmark-covers")
    .upload(`${userId}/${Date.now()}.jpg`, formData);

  return data?.path;
}
```

### 5.3 离线能力

**问题**：移动端网络不稳定，需要离线浏览。

**方案**：**Service Worker (Web) + Capacitor Filesystem (App) + 小程序缓存**

```typescript
// App 端：使用 @capacitor/preferences 存储关键数据
import { Preferences } from "@capacitor/preferences";

export async function cacheBookmarks(bookmarks: Bookmark[]) {
  await Preferences.set({
    key: "cached_bookmarks",
    value: JSON.stringify(bookmarks),
  });
}

// 小程序端：使用 Taro.setStorage
Taro.setStorageSync("cached_bookmarks", bookmarks);
```

## 8. 成本与收益分析

### 8.1 开发成本

- **App (Capacitor)**：低（复用 85% 代码，主要做原生能力封装）
- **小程序 (Taro)**：中（需要适配组件，但逻辑可复用）
- **总工时估算**：6-8 周（1 名全栈工程师）

### 8.2 运营成本

- **App Store 年费**：$99/年（iOS）
- **Google Play 一次性**：$25（Android）
- **小程序认证**：¥300/年（微信）

### 8.3 收益预期

- **用户增长**：移动端用户通常占 60-70%
- **使用频率**：移动端用户打开频率是 Web 的 3-5 倍
- **商业化**：App 内购转化率通常高于 Web

## 9. 风险与应对

### 9.1 小程序审核风险

**风险**：微信小程序审核严格，可能因"内容聚合"类目被拒。

**应对**：

- 申请"工具 > 信息收集"类目
- 准备详细的功能说明文档
- 如被拒，考虑转为"企业小程序"（需认证）

### 9.2 App 性能风险

**风险**：Capacitor 打包的 App 体积较大（通常 20-30MB）。

**应对**：

- 使用 Next.js 静态导出，减少运行时
- 图片懒加载和 CDN 加速
- 考虑使用 Capacitor 的"混合模式"（部分页面原生）

### 9.3 数据同步风险

**风险**：三端数据不一致，导致用户体验差。

**应对**：

- 使用 Supabase Realtime 实时同步
- 实现乐观更新（UI 立即响应，后台同步）
- 增加冲突解决机制（最后写入获胜）

## 11. 总结

AnyKeep 的技术栈（Next.js + React + TypeScript + Supabase）非常适合扩展到移动端：

- **App (Capacitor)**：几乎零成本，复用 85% 代码，主要做原生能力封装
- **小程序 (Taro)**：中等成本，复用 80% 代码，需要适配组件

**建议先完善 App，再开发小程序**，因为：

1. App 的代码复用率更高
2. App 的审核风险更低
3. App 的原生能力更强（分享接收、后台任务）
