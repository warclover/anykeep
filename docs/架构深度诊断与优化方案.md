## 二、根因诊断

### 根因 #1: 三重通信系统并存

**现象**：系统中存在三套相互交织的通信机制

```
┌─────────────────────────────────────────────────────────────┐
│                    通信系统现状                              │
├─────────────────────────────────────────────────────────────┤
│                                                             │
│  ┌──────────────┐    ┌──────────────┐    ┌──────────────┐  │
│  │ Window Event │◄──►│ HomePageCtx  │◄──►│  EventBus    │  │
│  │  (49 调用)    │    │  (桥接层)     │    │  (后端协调)   │  │
│  └──────────────┘    └──────────────┘    └──────────────┘  │
│         │                   │                   │          │
│         ▼                   ▼                   ▼          │
│    UI 组件通信          状态管理           系统级事件        │
│  (Header/Filter)     (筛选/视图模式)    (分类/摘要/组织)     │
└─────────────────────────────────────────────────────────────┘
```

**根本原因**：

1. **历史演进**：最初用 Window Event 实现跨组件通信
2. **局部优化**：Phase 3 引入 Context 但保留 Event Bridge 兼容
3. **后端需求**：EventBus 用于服务端三系统协调

**联动影响**：

- ❌ 状态可能不一致（Event 丢失、Context 延迟）
- ❌ 调试困难（需同时追踪三个系统）
- ❌ 内存泄漏风险（Event Listener 未清理）
- ❌ 新人上手成本高

**证据**：

```typescript
// home-page-context.tsx 第 225-262 行 - 双向桥接
const setViewMode = useCallback((mode: ViewMode) => {
  setViewModeState(mode);
  localStorage.setItem(VIEW_MODE_STORAGE_KEY, mode);
  // Event Bridge: 同步到旧系统
  window.dispatchEvent(new CustomEvent("viewModeChange", { detail: mode }));
}, []);
```

### 根因 #2: 数据获取策略碎片化

**现象**：相同类型的数据使用不同的获取和缓存策略

| 数据类型 | 获取方式      | 缓存策略                 | 文件                   |
| -------- | ------------- | ------------------------ | ---------------------- |
| 首页书签 | SWR + 聚合API | SWR缓存 + localStorage   | `use-init-data.ts`     |
| 书签列表 | SWR           | 自定义缓存层             | `use-bookmarks-swr.ts` |
| 文件夹   | 手动 fetch    | dataCache + localStorage | `use-page-data.ts`     |
| 统计数据 | 手动 fetch    | **无缓存**               | `use-page-data.ts`     |
| 搜索结果 | 手动 fetch    | **无缓存**               | `use-page-data.ts`     |
| 用户设置 | API fetch     | **无缓存**               | `use-page-data.ts`     |

**根本原因**：

1. **缺乏数据层规范**：没有统一的数据获取抽象
2. **渐进式优化**：不同时期添加的功能采用不同方案
3. **过度灵活**：开发者可自由选择获取方式

**联动影响**：

- ❌ 缓存失效不一致（SWR 自动失效 vs dataCache 手动失效）
- ❌ 重复请求（相同数据多处获取）
- ❌ 内存占用高（多套缓存系统）
- ❌ 性能优化困难（需逐个修改）

**证据**：

```typescript
// use-page-data.ts - 手动 fetch 无统一缓存
const { data: bookmarks, error } = await supabase
  .from("bookmarks")
  .select("*")
  .eq("user_id", user.id);

// use-init-data.ts - SWR 模式
const { data, error, isLoading, mutate } = useSWR<InitData>(url, fetcher, {
  dedupingInterval: 300_000,
  keepPreviousData: true,
});
```

### 根因 #3: Hook 职责边界模糊

**现象**：43 个 Hook 分布混乱，职责重叠

```
hooks/
├── use-bookmark-actions.ts    # 书签操作（与 home-mutations 重叠）
├── use-page-data.ts           # 页面数据（4个不同数据类型）
├── use-init-data.ts           # 初始数据（与 page-data 重叠）
├── use-folders.ts             # 文件夹（与 page-data 重叠）
├── use-smart-lists.ts         # 智能列表
├── use-classification-polling.ts  # 分类轮询
├── use-processing-poller.ts   # 处理轮询（与上面类似）
└── ... 36 more hooks
```

**根本原因**：

1. **按功能点创建**：每个新功能创建新 Hook
2. **缺乏分层设计**：没有 core/domain/ui 分层
3. **复用不足**：相似功能重复实现

**联动影响**：

- ❌ 重复代码（多个 Hook 做相似的事）
- ❌ 难以发现已有 Hook（无分类）
- ❌ 测试困难（依赖关系复杂）
- ❌ 性能问题（多个 Hook 独立发起请求）

**证据**：

```typescript
// use-home-bookmarks.ts - 同时使用两个数据源
const { bookmarks: initBookmarks } = useInitData({ enabled: shouldUseInitData });
const { data: bookmarks } = useBookmarksSWR({ ... });
// 需要复杂逻辑判断用哪个
```

### 根因 #4: 模块循环依赖

**现象**：event-bus 模块存在循环导入

```
event-bus/index.ts
    ↓ exports
system-coordinator.service.ts
    ↓ imports from
event-bus/index.ts  ← 循环！
```

**根本原因**：

- `index.ts` 导出 `SystemCoordinatorService`
- `SystemCoordinatorService` 需要导入 `eventBus` 和事件常量
- 形成 A→B→A 循环

**联动影响**：

- ❌ 模块加载顺序不确定
- ❌ 可能导致运行时错误
- ❌ 难以进行代码分割

**证据**：

```typescript
// event-bus/index.ts 第 37-43 行
export {
  SystemCoordinatorService,
  initSystemCoordinator,
} from "./system-coordinator.service";

// system-coordinator.service.ts 第 21-29 行
import { eventBus, ClassificationEvents, OrganizationEvents } from "./index"; // ← 循环导入
```

### 根因 #5: API 调用无统一入口

**现象**：组件直接调用 API，无统一管理

```typescript
// 64 处直接 fetch 调用分布在 43 个组件中
// 例如：
fetch("/api/bookmarks/batch-move", { ... });  // bookmark 组件
fetch("/api/folders/suggestions", { ... });   // folder 组件
fetch("/api/classification/classify", { ... }); // classification 组件
```

**根本原因**：

1. **无 API 客户端层**：组件直接调用 fetch
2. **无请求拦截器**：认证、错误处理重复实现
3. **无 Mock 能力**：测试困难

**联动影响**：

- ❌ 重复的错误处理逻辑
- ❌ 难以全局修改 API 行为
- ❌ 无法统一添加日志/监控
- ❌ 测试需要 Mock 网络层

### 根因 #6: 组件与数据强耦合

**现象**：组件直接依赖具体数据获取实现

```
HomePageClient
    ├── useInitData()        # 直接依赖
    ├── useBookmarksSWR()    # 直接依赖
    ├── useClassificationPolling()  # 直接依赖
    ├── useDialogs()         # 直接依赖
    └── ... 8 more hooks
```

**根本原因**：

1. **无依赖注入**：Hook 在组件内直接调用
2. **无状态管理层**：数据散落在各 Hook 中
3. **无服务层抽象**：业务逻辑混在 Hook 里

**联动影响**：

- ❌ 组件难以复用（携带大量依赖）
- ❌ 单元测试困难（需 Mock 多个 Hook）
- ❌ 性能优化受限（无法集中控制）

## 四、系统性解决方案

### 设计原则

1. **渐进式迁移**：不破坏现有功能，逐步替换

3. **模块边界清晰**：每个模块职责单一，依赖明确
4. **可测试性优先**：所有改动必须可单元测试

### Phase 1: 统一事件系统（解决根因#1）

**目标**：消除 Window Event，统一到 Context + EventBus

**实施步骤**：

#### 1.1 标记所有 Window Event 调用点

```bash
# 已识别 49 处，分布在 21 个文件
# 主要集中在：
# - home-page-context.tsx (15 处) - 桥接层
# - header-menu.tsx (4 处)
# - platform-filter.tsx (3 处)
# - usage-tag-filter-sheet.tsx (2 处)
```

#### 1.2 创建统一的 UIEventBus

```typescript
// lib/events/ui-event-bus.ts
type UIEventMap = {
  "view:mode:change": { mode: ViewMode };
  "view:layout:change": { mode: LayoutMode };
  "filter:platform:change": { platform: string };
  "filter:folder:change": { folder: string };
  "filter:usageTags:change": { tags: string[] };
  "dialog:open": { type: DialogType };
  "dialog:close": void;
  "selection:toggle": { enabled: boolean };
};

class UIEventBus extends EventEmitter<UIEventMap> {
  private static instance: UIEventBus;

  static getInstance(): UIEventBus {
    if (!this.instance) {
      this.instance = new UIEventBus();
    }
    return this.instance;
  }
}

export const uiEventBus = UIEventBus.getInstance();
```

#### 1.3 迁移 HomePageContext

```typescript
// contexts/home-page-context.tsx (改造后)
export function HomePageProvider({ children }: Props) {
  // 状态保持不变
  const [viewMode, setViewModeState] = useState<ViewMode>(DEFAULT_VIEW_MODE);

  // 移除 Window Event，使用 UIEventBus
  const setViewMode = useCallback((mode: ViewMode) => {
    setViewModeState(mode);
    localStorage.setItem(VIEW_MODE_STORAGE_KEY, mode);
    // 替换: window.dispatchEvent → uiEventBus.emit
    uiEventBus.emit("view:mode:change", { mode });
  }, []);

  // 移除 Event Bridge 监听
  // useEffect 中的 window.addEventListener 全部移除
}
```

#### 1.4 组件迁移

```typescript
// 迁移前
window.dispatchEvent(new CustomEvent("viewModeChange", { detail: mode }));

// 迁移后
uiEventBus.emit("view:mode:change", { mode });
```

**风险控制**：

- 每个组件单独迁移，单独测试
- 保留 `enableEventBridge` 开关，可快速回滚
- 添加废弃警告，记录使用旧 API 的调用

### Phase 2: 统一数据获取层（解决根因#2, #5）

**目标**：建立统一的数据获取和缓存策略

#### 2.1 创建 API Client 层

```typescript
// lib/api/client.ts
import { authFetcher } from "./fetch-with-auth";

class APIClient {
  private baseURL = "/api";

  // 通用请求方法
  private async request<T>(
    endpoint: string,
    options?: RequestInit,
  ): Promise<T> {
    const url = `${this.baseURL}${endpoint}`;
    return authFetcher<T>(url, options);
  }

  // 书签相关 API
  bookmarks = {
    list: (params: BookmarkListParams) =>
      this.request<BookmarkListResponse>(
        `/bookmarks?${new URLSearchParams(params)}`,
      ),
    get: (id: number) => this.request<Bookmark>(`/bookmarks/${id}`),
    create: (data: CreateBookmarkData) =>
      this.request<Bookmark>("/bookmarks", {
        method: "POST",
        body: JSON.stringify(data),
      }),
    update: (id: number, data: Partial<Bookmark>) =>
      this.request<Bookmark>(`/bookmarks/${id}`, {
        method: "PATCH",
        body: JSON.stringify(data),
      }),
    delete: (id: number) =>
      this.request<void>(`/bookmarks/${id}`, { method: "DELETE" }),
    batchMove: (ids: number[], folderId: number) =>
      this.request<void>("/bookmarks/batch-move", {
        method: "POST",
        body: JSON.stringify({ ids, folderId }),
      }),
  };

  // 文件夹相关 API
  folders = {
    list: () => this.request<Folder[]>("/folders"),
    create: (data: CreateFolderData) =>
      this.request<Folder>("/folders", {
        method: "POST",
        body: JSON.stringify(data),
      }),
    // ...
  };

  // 初始化数据（聚合）
  init = (params?: InitParams) =>
    this.request<InitData>(`/init?${new URLSearchParams(params)}`);
}

export const apiClient = new APIClient();
```

#### 2.2 创建 Repository 层

```typescript
// lib/repositories/bookmark.repository.ts
import { apiClient } from "../api/client";
import { queryClient } from "../query-client";

export const bookmarkRepository = {
  // 查询键
  keys: {
    all: ["bookmarks"] as const,
    list: (params: BookmarkListParams) =>
      [...bookmarkRepository.keys.all, "list", params] as const,
    detail: (id: number) =>
      [...bookmarkRepository.keys.all, "detail", id] as const,
  },

  // 获取列表
  async getList(params: BookmarkListParams): Promise<Bookmark[]> {
    return queryClient.fetchQuery({
      queryKey: this.keys.list(params),
      queryFn: () => apiClient.bookmarks.list(params),
      staleTime: 5 * 60 * 1000, // 5 分钟
    });
  },

  // 创建
  async create(data: CreateBookmarkData): Promise<Bookmark> {
    const bookmark = await apiClient.bookmarks.create(data);
    // 自动失效相关缓存
    queryClient.invalidateQueries({ queryKey: this.keys.all });
    return bookmark;
  },

  // 乐观更新
  async update(id: number, data: Partial<Bookmark>): Promise<Bookmark> {
    // 乐观更新
    const previousBookmarks = queryClient.getQueryData(this.keys.all);
    queryClient.setQueryData(this.keys.all, (old: Bookmark[]) =>
      old.map((b) => (b.id === id ? { ...b, ...data } : b)),
    );

    try {
      return await apiClient.bookmarks.update(id, data);
    } catch (error) {
      // 回滚
      queryClient.setQueryData(this.keys.all, previousBookmarks);
      throw error;
    }
  },
};
```
