> **版本**: v1.0

> **评估目标**: 中文/英文双语切换支持

## 1. 执行摘要

### 1.1 评估结论

| 维度           | 评估        | 说明                             |
| -------------- | ----------- | -------------------------------- |
| **技术可行性** | ✅ 完全可行 | Next.js App Router 原生支持 i18n |
| **实施复杂度** | ⚠️ 中等偏高 | 现有代码需大量改造               |
| **推荐方案**   | 预埋架构    | 先搭建基础，新代码遵循规范       |
| **最小投入**   | 2 天        | 基础设施 + 开发规范              |
| **完整实施**   | 13-17 天    | 全量翻译 + 测试                  |

### 1.2 核心建议

**推荐「方案 A: 预埋架构」**：先投入 2 天搭建 i18n 基础设施，新开发的功能使用 `t()` 函数，存量代码后续逐步迁移。

## 3. 技术方案对比

### 3.1 方案选项

| 方案                        | 优点                                | 缺点               | 适用场景     |
| --------------------------- | ----------------------------------- | ------------------ | ------------ |
| **next-intl**               | App Router 原生支持、类型安全、轻量 | 社区相对较小       | ✅ 推荐      |
| **i18next + react-i18next** | 生态丰富、功能强大                  | 配置复杂、包体积大 | 大型项目     |
| **lingui**                  | 编译时优化、ICU 标准                | 学习曲线陡峭       | 性能敏感场景 |
| **自研方案**                | 完全可控                            | 维护成本高         | ❌ 不推荐    |

### 3.2 推荐方案: next-intl

**选择理由**:

1. **App Router 原生支持** - 与 Next.js 14+ Server Components 完美集成
2. **类型安全** - TypeScript 类型推导，编辑器自动补全
3. **轻量级** - 包体积小（~15KB gzipped）
4. **渐进式采用** - 可逐步迁移，不需要一次性改造

**核心特性**:

```typescript
// Server Component 中使用
import { getTranslations } from 'next-intl/server';

export default async function Page() {
  const t = await getTranslations('HomePage');
  return <h1>{t('title')}</h1>;
}

// Client Component 中使用
'use client';
import { useTranslations } from 'next-intl';

export function Button() {
  const t = useTranslations('Common');
  return <button>{t('submit')}</button>;
}
```

## 8. 实施方案

### 8.1 方案 A: 预埋架构（推荐）

**策略**: 先搭建基础设施，新代码遵循规范，存量逐步迁移

**第一周（2 天）**:

1. 安装 next-intl 及相关依赖
2. 创建 [locale] 路由结构
3. 实现语言检测中间件
4. 创建语言切换组件
5. 编写开发规范文档
6. 迁移 1-2 个示例页面

**后续迭代**:

- 每个新功能必须支持 i18n
- 每个 Sprint 迁移 5-10 个现有组件
- 预计 6-8 周完成全量迁移

**优点**:

- 投入小，见效快
- 不影响当前开发进度
- 渐进式改进，风险可控

**缺点**:

- 完成周期长
- 临时存在中英混合状态

### 8.2 方案 B: 集中改造

**策略**: 集中 2-3 周时间完成全量改造

**时间线**:

- 第 1 周: 基础设施 + 核心页面
- 第 2 周: 剩余组件 + 错误消息
- 第 3 周: 翻译审校 + 测试

**优点**:

- 快速完成，状态一致
- 翻译工作集中处理

**缺点**:

- 需要暂停其他开发
- 风险集中

### 8.3 方案 C: 延后实施

**策略**: 等核心功能稳定后再考虑

**条件**:

- 完成 MVP 功能
- 有明确的国际化用户需求
- 有专门的翻译资源

**优点**:

- 当前专注核心功能
- 避免过早优化

**缺点**:

- 后期改造成本更高
- 代码耦合度增加

## 9. 实施建议

### 9.1 推荐路径

```
当前状态                    推荐路径                      长期目标
─────────────────────────────────────────────────────────────────
无 i18n 支持      →     方案 A: 预埋架构      →      完整双语支持
                        (2 天投入)                   (6-8 周完成)
```

### 9.2 具体建议

1. **近期（1-2 周内）**:
   - 采用「方案 A: 预埋架构」
   - 投入 2 天搭建 i18n 基础设施
   - 建立开发规范，新功能必须使用 `t()` 函数

2. **中期（1-2 个月）**:
   - 每个 Sprint 迁移部分存量代码
   - 优先迁移用户高频使用页面
   - 建立翻译文件维护流程

3. **长期（2-3 个月）**:
   - 完成全量迁移
   - 引入专业翻译审校
   - 考虑支持更多语言

### 9.3 不建议做的事

1. ❌ 一次性全量改造（风险高、影响开发进度）
2. ❌ 自研 i18n 方案（维护成本高）
3. ❌ 使用机器翻译直接上线（质量无保证）
4. ❌ 延迟到 MVP 完成后（改造成本更高）

### 11.2 关键代码示例

```typescript
// src/i18n/request.ts
import { getRequestConfig } from "next-intl/server";
import { cookies } from "next/headers";

export default getRequestConfig(async () => {
  const cookieStore = await cookies();
  const locale = cookieStore.get("NEXT_LOCALE")?.value || "zh-CN";

  return {
    locale,
    messages: (await import(`../../messages/${locale}.json`)).default,
  };
});
```

```typescript
// src/middleware.ts
import createMiddleware from "next-intl/middleware";
import { locales, defaultLocale } from "./i18n/config";

export default createMiddleware({
  locales,
  defaultLocale,
  localeDetection: true,
});

export const config = {
  matcher: ["/((?!api|_next|.*\\..*).*)"],
};
```

## 12. 结论

AnyKeep 项目实现多语言功能**技术上完全可行**，推荐采用**「方案 A: 预埋架构」**：

1. **立即投入 2 天**搭建 i18n 基础设施
2. **新功能必须**使用 `t()` 函数
3. **逐步迁移**存量代码（6-8 周）
4. **暂缓**完整翻译，等核心功能稳定后再投入

这样既能为未来国际化打下基础，又不影响当前开发进度。
