# API 版本碎片化 — 安全迁移与治理方案

> 目标：在**不影响现有功能**的前提下，逐步收敛 API 版本、统一前端调用、明确废弃时间表。  
> 状态：**方案稿，待审核**

---

## 一、问题与教训

### 1.1 现状

- **书签**：`/api/bookmarks/` 与 `/api/v1/bookmarks/` 并存，能力与响应结构不完全一致。
- **分类**：`/api/classification/v2/`、`/api/classification/v5/`、v5.5 概念并行，新人难以选择。
- **影响**：前端调用分散在多版本；维护成本高；一旦「一刀切」迁移易引发线上故障。

### 1.2 上次优化为何出问题（根因归纳）

| 根因类型             | 说明                                                                                                    | 导致的表象                                     |
| -------------------- | ------------------------------------------------------------------------------------------------------- | ---------------------------------------------- |
| **响应结构未对齐**   | 前端仍按旧版 `data.bookmarks` / `data.pagination` 解析，v1 返回 `data.items` / `data.hasMore`，未做适配 | 列表不展示、快速收藏后看不到、删除依赖列表失效 |
| **行为未等价**       | v1 创建书签只写库，未触发摘要/标签/元数据等后续链路                                                     | AI 摘要失效、AI 标签失效、首页图失效           |
| **前端未成对迁移**   | 只改 API 路径常量，未改响应解析与调用方逻辑                                                             | 快速收藏、删除、列表、卡片等多处异常           |
| **类型与契约不一致** | 如批量删除 `ids` 仅接受 number[]，前端部分传 string[]                                                   | 删除等接口报错或静默失败                       |

**结论**：治理 API 碎片化的前提是「**先等价、再切换；先适配、再废弃**」，不能只改路径或只改后端而不改前端解析与行为。

---

## 二、设计原则（保障功能不受影响）

1. **行为等价优先**：任一能力从旧版迁到 v1 前，v1 必须实现与旧版相同的业务行为（含异步任务、侧效、响应结构或可被适配）。
2. **双轨运行期**：迁移期内旧版与 v1 同时可用；不通过「关闭旧版」倒逼前端，而是用「推荐路径 + 废弃时间表」逐步收敛。
3. **契约先行**：先定 v1 的请求/响应契约（含字段名、分页结构、错误码），再让前端按契约适配；旧版可加适配层输出与 v1 同构的数据，便于前端统一解析。
4. **按调用点分批迁移**：按功能域（如首页列表、快速收藏、删除、分类入口）逐个迁移并验收，再考虑废弃旧路径。
5. **可观测与回滚**：关键调用可打标（如 header 或 query）区分新旧路径，便于监控与快速回滚。

---

## 三、可落地方案总览

```
Phase 0：契约与清单（不删不改，只做摸底）
    → 产出：v1 与旧版能力/响应差异清单、推荐契约

Phase 1：v1 行为等价 + 响应兼容层
    → 产出：v1 能力与旧版对齐；前端统一「响应适配层」可同时消费 v1 与旧版

Phase 2：前端按域迁移到 v1
    → 产出：各域切到 v1 并验收，旧版仅作兜底

Phase 3：废弃时间表与下线
    → 产出：308/410 与文档，最终移除旧版
```

---

## 四、Phase 0：契约与清单（约 1～2 天）

### 4.1 目标

- 不删除、不重定向任何现有 API。
- 明确「书签 v1 vs 旧版」「分类 v2/v5」的能力与响应差异，形成清单与推荐契约。

### 4.2 动作

| 序号 | 动作                                                                                                                                          | 产出                                           |
| ---- | --------------------------------------------------------------------------------------------------------------------------------------------- | ---------------------------------------------- |
| 0.1  | 列出所有**书签**相关前端调用点（列表、创建、详情、删除、批量、metadata、generate-tags 等）及当前使用的路径（常量或硬编码）                    | `docs/api-bookmark-call-sites.md` 或表格       |
| 0.2  | 对比旧版与 v1 的**请求体/查询参数**与**响应体**（字段名、分页结构、错误格式），记入同一文档                                                   | 同上，增加「请求/响应差异」章节                |
| 0.3  | 列出**分类**相关调用点及使用的 v2/v5 路径；标注 v5 独有能力（shadow、metrics 等）与 v2 共有能力                                               | `docs/api-classification-call-sites.md` 或表格 |
| 0.4  | 定稿「书签 v1 推荐契约」：列表响应用 `{ data: { items, total, limit, offset, hasMore } }` 还是兼容一层 `bookmarks`/`pagination`，错误体格式等 | 写入 `docs/api-v1-contract.md`                 |

### 4.3 验收

- 产品/前端/后端对「差异清单」与「v1 推荐契约」无异议，可作为后续开发与测试的基准。

---

## 五、Phase 1：v1 行为等价 + 响应兼容层（约 1～2 周）

### 5.1 目标

- v1 在「创建、列表、删除、批量操作」等路径上，**业务行为**与旧版对齐（含 AI 摘要/标签、元数据/封面、分类等后续链路）。
- 前端只需面对**一套响应形状**，无论请求发往 v1 还是旧版，都通过**适配层**解析，避免因结构不一致导致白屏或功能失效。

### 5.2 后端：v1 行为等价

| 能力        | 当前缺口（v1 相对旧版）                                             | 动作                                                                                                  |
| ----------- | ------------------------------------------------------------------- | ----------------------------------------------------------------------------------------------------- |
| 创建书签    | 创建后未触发摘要/标签/元数据                                        | 在 v1 POST 创建成功后，复用或调用与旧版相同的「摘要+标签」及可选「元数据/封面」流程（同步或入队 job） |
| 列表        | 响应为 `items`/`hasMore`，旧端期望 `bookmarks`/`pagination.hasMore` | 见 5.3：由前端适配层统一；或 v1 在响应中增加兼容字段（如 `data.bookmarks = data.items`）二选一        |
| 批量删除    | `ids` 类型 strict                                                   | 已可用 `z.coerce.number()` 等做兼容；确保错误信息明确                                                 |
| 元数据/封面 | v1 创建不拉取 og:image 等                                           | 在 v1 创建后入队「元数据/封面」任务，或与摘要 job 合并为同一 pipeline                                 |

### 5.3 前端：统一响应适配层

- **位置建议**：在 `useBookmarksSWR`、`fetchFromAPI` 或统一 fetch 封装处。
- **逻辑**：根据响应结构自动识别版本并归一化：
  - 若存在 `data.items` 且存在 `data.hasMore` → 视为 v1，归一为 `{ bookmarks: data.items, hasMore: data.hasMore }`（或项目内约定的统一结构）。
  - 若存在 `data.bookmarks` 与 `data.pagination` → 视为旧版，同样映射到同一内部结构。
- **效果**：列表、加载更多、删除后刷新等逻辑只依赖「统一结构」，不关心请求发往 v1 还是旧版，降低切换风险。

### 5.4 分类：暂不合并 v2/v5 路径，只做「推荐约定」

- 在文档与常量注释中明确：**分类执行与规则**以 v2 为准；v5 仅保留独有能力（shadow、metrics、t1-stream 等）。
- 不在本阶段删除或 308 v5 的 classify/batch/feedback/rules，避免影响现有调用；仅新增/修改的代码推荐走 v2。

### 5.5 验收

- 使用 **v1 且仅 v1** 完成：创建书签 → 列表展示 → 删除 → 列表更新；新建书签在约定时间内出现 AI 摘要与标签；封面/元数据按设计补齐或入队。
- 使用**旧版**路径再跑一遍上述流程，行为一致（若旧版仍被部分页面使用）。
- 前端适配层单测或集成测试：对「v1 形状」「旧版形状」两种 mock 响应均解析为同一内部结构。

## 六、Phase 2：前端按域迁移到 v1（约 1～2 周）

### 6.1 策略

- 按**功能域**分批把请求从旧版改为 v1（常量改为 `API_PATHS.bookmarks.*` 等），每批完成后做该域回归。
- 依赖 Phase 1 的「行为等价」与「响应适配层」，切换路径后不应改变 UI 行为。

### 6.2 建议批次

| 批次 | 域                                     | 涉及路径示例                   | 验收方式                                            |
| ---- | -------------------------------------- | ------------------------------ | --------------------------------------------------- |
| 2.1  | 首页列表与加载更多                     | GET list, loadMore             | 列表展示、分页、筛选、排序正常                      |
| 2.2  | 快速收藏（FAB/QuickAdd）               | POST create                    | 创建成功、列表或乐观更新出现新项、摘要/标签后续生成 |
| 2.3  | 首页卡片删除/批量操作                  | batch/delete, batch/restore 等 | 删除/恢复后列表与缓存一致                           |
| 2.4  | 书签详情与编辑                         | GET/PATCH detail               | 详情加载、保存、跳转正常                            |
| 2.5  | 其他书签相关（整理页、文件夹内列表等） | list, detail, batch\*          | 各页功能与旧版一致                                  |
| 2.6  | 分类相关（若本阶段要做）               | 仅新调用走 v2；旧调用暂保留    | 新功能用 v2，旧功能无回归                           |

### 6.3 每批动作

1. 将该域内请求路径改为 v1（或 v2 分类）。
2. 确认响应仍经「适配层」解析（若该域已用统一封装）。
3. 该域功能测试 + 关键路径 E2E（若有）。
4. 提交与发布，观察错误率/埋点（若有）。

### 6.4 验收

- 所有计划迁移的域均已切到 v1（或约定版本），且无已知回归。
- 文档中更新「推荐 API」与「已迁移调用点」清单。

---

## 七、Phase 3：废弃时间表与下线（按需，建议 1～3 个月后）

### 7.1 废弃策略

- 在旧版响应中增加头（如 `X-API-Deprecated: true`、`Sunset: <date>`），并在文档注明废弃时间。
- 到约定日期后，旧版返回 **308 重定向**到 v1（或 410 Gone），并保留至少一个版本周期便于排查。
- 再经过一个周期后，移除旧版实现或仅保留 410。

### 7.2 时间表示例（可调整）

| 阶段     | 内容                                                           | 建议时间       |
| -------- | -------------------------------------------------------------- | -------------- |
| 公告     | 文档与响应头标明「旧版书签 API 将于 YYYY-MM 废弃」             | Phase 2 完成后 |
| 308      | 旧版 GET/POST 返回 308 指向 v1，并保留旧版实现一段时间以便回滚 | 公告后 4～8 周 |
| 410/移除 | 旧版返回 410 或移除路由                                        | 308 后 2～4 周 |

分类 v5 与 v2 的合并可单独排期，原则相同：先行为等价与推荐约定，再 308/410。

## 八、风险与缓解

| 风险                        | 缓解                                                                             |
| --------------------------- | -------------------------------------------------------------------------------- |
| v1 与旧版行为仍不一致       | Phase 1 用清单逐项对照（创建、列表、删除、AI、元数据），并用自动化或手工用例覆盖 |
| 前端某处未走适配层          | Phase 0 清单覆盖所有调用点；Phase 2 按域迁移时逐点确认使用的封装                 |
| 废弃后仍有调用方未迁        | 通过监控/日志识别仍访问旧路径的客户端，在 Sunset 前通知并预留回滚窗口            |
| 分类 v2/v5 混用导致逻辑错误 | 本方案先不合并分类路径，只做推荐与文档；合并前单独做「分类能力对照」与回归       |

## 十、小结

- **为何上次会出问题**：在 v1 与旧版「响应结构不一致、行为不等价」的情况下，仅改路径或常量，导致前端解析错误与能力缺失。
- **本次如何保障功能**：先通过 **Phase 0 清单 + Phase 1 行为等价与响应适配层** 做到「用 v1 也能得到与旧版一致的结果与体验」，再在 **Phase 2 按域迁移**，最后在 **Phase 3** 才执行废弃与下线。
- **建议审核顺序**：先确认 Phase 0 的差异清单与 v1 契约 → 再确认 Phase 1 的等价项与适配层设计 → 最后确认 Phase 2 批次与 Phase 3 时间表是否可接受。
