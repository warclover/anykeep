# 两套确认系统调研及方案

> 日期：2024-12-24

## 一、问题背景

在 AI Skills 架构升级过程中，发现 Agent 和 Skills 存在两套独立的确认系统，造成：

- 前端需要处理两种不同的确认格式
- 后端维护成本增加
- 用户体验不一致

## 二、当前架构对比

| 维度         | Agent 确认系统                          | Skills 确认系统                                   |
| ------------ | --------------------------------------- | ------------------------------------------------- |
| **位置**     | `ai-agent/core/confirmation-handler.ts` | `ai-skills/orchestration/confirmation-handler.ts` |
| **API**      | `/api/agent/confirm`                    | 无独立 API（嵌入流式响应）                        |
| **触发方式** | Tool 标记 `requiresConfirmation`        | Skill 调用 `emitConfirmation()`                   |
| **状态枚举** | `pending/confirmed/cancelled/expired`   | `pending/confirmed/rejected/expired/cancelled`    |
| **存储**     | 内存 Map + TTL                          | 内存 Map + TTL                                    |
| **使用场景** | 单次工具调用（删除、批量操作）          | 多步骤编排中间确认                                |

### 本质问题

这不仅仅是"两套确认系统"的问题，而是**两种执行范式的边界模糊**导致的架构裂缝：

```
┌─────────────────────────────────────────────────────────────────────┐
│                           根本矛盾                                   │
├─────────────────────────────────────────────────────────────────────┤
│  原子模式 (Agent)          ↔          编排模式 (Skills)             │
│  ─────────────────              ─────────────────────               │
│  • 请求-响应式                   • 流式多步骤                       │
│  • 工具调用为核心                • Skill 编排为核心                 │
│  • 确认=暂停工具执行             • 确认=流程节点决策                │
│  • 无状态（确认后重新执行）      • 有状态（确认后继续执行）         │
└─────────────────────────────────────────────────────────────────────┘
```

**关键洞察**：两套确认系统的隔离是**表象**，真正的架构债务是：

1. UnifiedEngine 统一了入口，但没有统一副作用处理
2. 确认是副作用的一种，还有：通知、存储、审计日志等
3. 如果只解决确认隔离，未来会遇到同样的问题

## 四、方案对比

### 方案 A：统一到流式确认

**核心思路**：废弃 `/api/agent/confirm`，所有确认都通过流式响应处理

```typescript
// 统一确认协议
interface UnifiedConfirmation {
  type: "confirmation";
  data: {
    id: string;
    source: "tool" | "skill"; // 来源标识
    title: string;
    message: string;
    options: ConfirmOption[];
    preview?: unknown;
    contextData?: Record<string, unknown>;
    expiresAt: string;
  };
}
```

**优点**：

- 前端只需处理一种确认格式
- 用户体验一致（都在对话流中确认）
- 代码复用最大化

**缺点**：

- 实现复杂度高
- 需要迁移现有逻辑

### 方案 B：双轨并行 + 统一前端适配器

**核心思路**：保持后端隔离，但在前端统一处理

```typescript
// 前端统一适配器
class ConfirmationAdapter {
  detectSource(chunk: StreamChunk): "tool" | "skill" | null {
    if (chunk.type === "confirmation") return "skill";
    if (chunk.type === "tool_call" && chunk.requiresConfirmation) return "tool";
    return null;
  }

  async handleConfirmation(
    confirmation: ToolConfirmation | SkillConfirmation,
    userResponse: boolean
  ): Promise<void> {
    const source = this.detectSource(confirmation);
    if (source === "tool") {
      await fetch("/api/agent/confirm", { ... });
    } else {
      await this.sendConfirmationResponse(confirmation.id, userResponse);
    }
  }
}
```

**优点**：

- 后端改动最小
- 渐进式迁移

**缺点**：

- 前端复杂度增加
- 两套后端代码仍需维护

### 方案 C：统一到 Tool 确认（不推荐）

将 Skills 确认改为调用 Tool，通过 `/api/agent/confirm` 处理。

**缺点**：

- 破坏 Skills 的流式编排特性
- 确认后无法恢复多步骤执行上下文

## 五、推荐方案：副作用统一层 (Effect Layer)

### 架构设计

```
┌─────────────────────────────────────────────────────────────────────┐
│                      /api/agent/unified                              │
└────────────────────────────┬────────────────────────────────────────┘
                             │
┌────────────────────────────▼────────────────────────────────────────┐
│                       UnifiedEngine                                  │
│               (路由决策 + 执行协调)                                   │
└────────────────────────────┬────────────────────────────────────────┘
                             │
        ┌────────────────────┼────────────────────┐
        │                    │                    │
        ▼                    ▼                    ▼
┌──────────────┐    ┌──────────────┐    ┌──────────────────────────┐
│ Atomic Mode  │    │Orchestration │    │  ✨ Effect Layer (新增)   │
│              │    │    Mode      │    │  ─────────────────────   │
│              │    │              │    │  • ConfirmationService   │
│              │    │              │    │  • NotificationService   │
│              │    │              │    │  • AuditLogService       │
│              │    │              │    │  • StateSnapshotService  │
└──────┬───────┘    └──────┬───────┘    └────────────┬─────────────┘
       │                   │                         │
       └───────────────────┴─────────────────────────┘
                           │
                           ▼
                  统一的副作用处理
```

### Effect Layer 核心设计

```typescript
// src/lib/ai-skills/effects/types.ts
interface EffectContext {
  requestId: string;
  userId: string;
  mode: "atomic" | "orchestration";
  source: "tool" | "skill";
}

interface Effect<T = unknown> {
  type: "confirmation" | "notification" | "audit" | "state";
  payload: T;
  context: EffectContext;
}

// 统一的确认副作用
interface ConfirmationEffect extends Effect<ConfirmationPayload> {
  type: "confirmation";
  payload: {
    id: string;
    title: string;
    message: string;
    options: ConfirmOption[];
    preview?: unknown;
    timeout: number;
    onConfirm: () => Promise<void>;
    onCancel: () => Promise<void>;
  };
}
```

```typescript
// src/lib/ai-skills/effects/effect-manager.ts
class EffectManager {
  private handlers: Map<string, EffectHandler>;

  async emit<T>(effect: Effect<T>): Promise<EffectResult> {
    const handler = this.handlers.get(effect.type);
    return handler.handle(effect);
  }

  toStreamChunk(effect: Effect): UnifiedStreamChunk {
    return {
      type: effect.type,
      data: {
        ...effect.payload,
        source: effect.context.source,
        mode: effect.context.mode,
      },
    };
  }
}
```

## 六、分阶段实施路径

### Phase 0: 立即行动（0-1 周）

**目标**：不改后端，前端统一

```typescript
// src/hooks/domain/ai/use-unified-confirmation.ts
export function useUnifiedConfirmation() {
  const handleAnyConfirmation = useCallback(
    async (chunk: UnifiedStreamChunk, userChoice: string) => {
      const source = chunk.data?.source ?? detectSource(chunk);

      if (source === "tool") {
        return handleToolConfirmation(chunk, userChoice);
      } else {
        return handleSkillConfirmation(chunk, userChoice);
      }
    },
    [],
  );

  return { handleAnyConfirmation };
}
```

## 八、设计原则

### 1. 副作用隔离原则 (Effect Isolation)

```
❌ Bad:  Tool/Skill 直接处理确认逻辑
✅ Good: Tool/Skill 发射 Effect，由统一层处理
```

### 2. 来源透明原则 (Source Transparency)

```
❌ Bad:  前端需要猜测确认来源
✅ Good: 每个 Effect 携带明确的 source 和 mode
```

### 3. 回调封装原则 (Callback Encapsulation)

```
❌ Bad:  确认后需要重新调用 API
✅ Good: Effect 携带 onConfirm/onCancel 回调
```

### 4. 向后兼容原则 (Backward Compatibility)

```
❌ Bad:  一次性替换，风险大
✅ Good: 新旧并行，逐步迁移
```

## 十、总结

**核心观点**：确认系统隔离是冰山一角，真正需要解决的是**副作用处理的统一架构**。

**行动建议**：

1. **立即**：实现前端统一适配（1 周内）
2. **短期**：增加后端 `ConfirmationAdapter`（2-3 周）
3. **中期**：构建完整的 `Effect Layer`（4-6 周）
