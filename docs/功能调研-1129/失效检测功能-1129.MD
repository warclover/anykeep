## 失效检测功能设计说明（AnyKeep）

**文档日期**：2025-11-29  
**文档版本**：V1.0  

本设计文档将「失效检测 + 自动归档到系统失效文件夹」从概念方案细化到**可直接供前后端开发实现**的层面，覆盖数据结构、后端流程、前端交互与配置项。

---

## 1. 功能目标与范围

### 1.1 功能目标

1. **定期检测收藏链接是否可访问**（HTTP 层面），识别 404/500/域名失效等情况。  
2. **自动将判定为失效的收藏移动到系统文件夹「失效收藏」**，便于统一管理与批量处理。  
3. **为用户提供恢复与清理能力**：可从失效文件夹中恢复或批量删除失效收藏。  
4. 与现有 **搜索 / 评级 / 分析** 体系协同工作，不破坏已有功能。

### 1.2 范围边界

- 仅检测「链接可访问性」，**不检测业务内容是否变更**（如文章被改）。  
- 默认只对 **外部 HTTP/HTTPS 链接** 进行检测：
  - `platform` 为微信/B 站/小红书/浏览器书签等。
  - 将来抖音模块接入后亦可复用。  
- 不对如下链接做失效判定：
  - 需要登录 / 权限页面（返回 200 但内容是登录页）——视为「特殊状态」，不归为失效。
  - `file://`、本地路径等非 HTTP 链接（可以直接标记为不检测）。

## 2. 数据模型与数据库设计

### 2.1 `bookmarks` 表字段扩展

在 `public.bookmarks` 中新增与链接健康相关字段：

```sql
ALTER TABLE public.bookmarks
ADD COLUMN link_status VARCHAR(20) NOT NULL DEFAULT 'unknown',
ADD COLUMN link_last_checked_at TIMESTAMPTZ,
ADD COLUMN link_failure_count INT NOT NULL DEFAULT 0;

COMMENT ON COLUMN public.bookmarks.link_status IS '链接状态: unknown, valid, invalid, timeout, login_required, error';
COMMENT ON COLUMN public.bookmarks.link_last_checked_at IS '最近一次链接健康检测的时间';
COMMENT ON COLUMN public.bookmarks.link_failure_count IS '连续检测失败次数（用于误判保护）';
```

状态定义：
- `unknown`：默认值，尚未检测或检测结果被清空。  
- `valid`：可访问（2xx/3xx）。  
- `invalid`：明确 4xx/5xx 或 DNS/域名解析失败。  
- `timeout`：请求超时（网络波动）。  
- `login_required`：响应为登录/权限页（启发式判断）。  
- `error`：其他错误（例如 TLS 错误等），暂不判死。  

> 注意：**只有满足一定规则时才将收藏移动到失效文件夹**，详见第 4 节。

### 2.2 `folders` 表系统失效文件夹

在现有系统文件夹机制基础上，新建系统文件夹类型：

```sql
-- 迁移中插入系统文件夹（伪代码示意）
INSERT INTO public.folders (user_id, name, parent_id, sort_order, is_system, system_type)
SELECT
  u.id AS user_id,
  '失效收藏' AS name,
  NULL AS parent_id,
  0 AS sort_order,
  TRUE AS is_system,
  'TRASH_BROKEN_LINKS' AS system_type
FROM auth.users u
WHERE NOT EXISTS (
  SELECT 1 FROM public.folders f
  WHERE f.user_id = u.id AND f.is_system = TRUE AND f.system_type = 'TRASH_BROKEN_LINKS'
);
```

约束与行为：
- `is_system = TRUE`，`system_type = 'TRASH_BROKEN_LINKS'`。  
- 不允许用户删除 / 重命名该文件夹（在 API 层阻止）。  
- 只允许通过：
  - 系统任务自动「移入」。
  - 用户手动将条目「移出」到其他普通文件夹。

> 若当前系统已有系统文件夹方案（如待整理等），可沿用相同创建逻辑，将该类型纳入统一枚举。

### 2.3 可选：记录原文件夹信息

为支持「还原到原路径」，可在 `bookmarks` 增加一个可选字段：

```sql
ALTER TABLE public.bookmarks
ADD COLUMN original_folder_id BIGINT;

COMMENT ON COLUMN public.bookmarks.original_folder_id IS '移动到失效收藏前所在的原文件夹 ID（可选）';
```

更新策略：
- 当系统首次将某条收藏移入失效文件夹时：
  - 若 `original_folder_id` 为 NULL：
    - 将当前 `folder_id` 记录到 `original_folder_id`。  
    - 将 `folder_id` 设置为失效系统文件夹 ID。  
- 当用户手动将其移出失效文件夹到新文件夹：
  - 可以选择：
    - 清空 `original_folder_id`，或
    - 保持最新「来源」逻辑，视实现复杂度而定。

## 3. 失效检测规则与判定逻辑

### 3.1 HTTP 级别判定

对每个 URL 发起 HEAD/GET 请求（建议优先 HEAD，失败再退回 GET）：

- 若获得响应：
  - `2xx / 3xx` → 标记为 `valid`，`link_failure_count` 归零。  
  - `4xx / 5xx` → 标记为 `invalid`，`link_failure_count + 1`。  
- 网络级错误（DNS/TLS 等）：
  - 标记为 `error`，`link_failure_count + 1`。  
- 超时：
  - 标记为 `timeout`，`link_failure_count + 1`。  

### 3.2 登录/权限页面判定（启发式）

若响应为 200 但内容包含典型登录页关键词（例如「登录」「密码」「验证码」「请先登录后访问」），可标记为：

- `link_status = 'login_required'`  
- 不计入 `link_failure_count` 或只做轻微增加（例如 +0.5），防止误判。

> 该部分可先简单实现（比如仅标记不影响失效判定），后续根据用户反馈再优化。

### 3.3 失效判定规则

为减少误判，采用「连续多次失败」策略：

- 参数（可配置）：
  - `FAILURE_THRESHOLD = 3`（连续失败次数）  
  - `FAILURE_WINDOW_DAYS = 7`（统计窗口天数）  

失效条件（满足任一即视为失效）：

1. `link_failure_count >= FAILURE_THRESHOLD`，且最近一次检测在 `FAILURE_WINDOW_DAYS` 内；  
2. `link_status` 为 `invalid` 且多次重试仍为 `invalid`（如 4xx 确定性错误）；  

对于 `timeout` / `error` 状态：
- 若偶发（少于阈值）→ 保持原文件夹，仅更新 `link_status` 与 `link_last_checked_at`。  
- 若长期多次超时 → 也可视为失效（计入 `link_failure_count`）。

### 3.4 判定结果对行为的影响

- 当判定为失效（满足 3.3 中条件）时：
  - 若当前 `folder_id != 失效收藏文件夹 ID`：
    - 如果 `original_folder_id` 为空，则记录当前 `folder_id` 到 `original_folder_id`。  
    - 将 `folder_id` 更新为失效收藏文件夹 ID。  
- 当后续检测恢复正常（少见，但可能）：
  - 可选策略：
    - 仅将 `link_status` 改回 `valid`，但收藏仍留在失效文件夹，由用户手动恢复；  
    - 或在「失效收藏」视图中标记「已恢复可访问」，方便用户批量还原。  

> 建议 v1 保守实现：**即便链接恢复，系统不自动移出失效文件夹，只提醒用户手动处理**。

## 4. 后端架构与实现步骤

### 4.1 失效检测核心服务（Node 模块）

位置建议：
- `src/lib/links/link-checker.ts`（新建）
- 如有现成的 `src/lib/browser-bookmark/link-validator.ts`，可重构为通用 HTTP 链接检测模块。

核心接口（示意）：

```ts
export interface LinkCheckResult {
  url: string;
  status: 'valid' | 'invalid' | 'timeout' | 'login_required' | 'error';
  statusCode?: number;
  responseTimeMs?: number;
  errorMessage?: string;
}

export interface LinkCheckOptions {
  timeoutMs?: number;
  maxConcurrent?: number;
}

export async function checkLinks(
  urls: string[],
  options?: LinkCheckOptions
): Promise<LinkCheckResult[]> {
  // 内部实现：并发请求 + 状态码解析 + 简单登录页检测
}
```

实现要点：
- 使用 `fetch`/`axios`/`node-fetch` 等发起请求。  
- 控制最大并发（如 5–10）与整体 timeout。  
- 对于相同域名的请求可以做简单限流（可选）。  

### 4.2 定期任务（Scheduler / Cron）

根据部署环境选择：
- 若使用 Vercel：使用 `Vercel Cron` 定时调用一个 API 路由；
- 若使用 Supabase Edge Functions：使用 `supabase functions schedule`；
- 或使用自建 `node-cron` + 常驻进程（不推荐在无状态环境中）。

#### 4.2.1 调度 API（示例：`/api/maintenance/link-check`）

职责：
1. 选出本次需要检测的一批书签 ID（分页）。  
2. 调用 `checkLinks` 模块。  
3. 根据结果更新数据库字段与文件夹归属。  

伪代码：

```ts
// GET /api/maintenance/link-check?batch=0&limit=200
export async function GET(req: NextRequest) {
  // 1. 解析分页参数
  const batch = Number(req.nextUrl.searchParams.get('batch') ?? '0');
  const limit = Number(req.nextUrl.searchParams.get('limit') ?? '200');

  // 2. 查询待检测书签（示例策略：按 link_last_checked_at 为空或最久未检查排序）
  const bookmarks = await db
    .from('bookmarks')
    .select('id, url, link_status, link_last_checked_at, link_failure_count, folder_id, user_id')
    .order('link_last_checked_at', { ascending: true, nullsFirst: true })
    .limit(limit)
    .offset(batch * limit);

  // 3. 调用检测服务
  const results = await checkLinks(bookmarks.map(b => b.url), { timeoutMs: 8000, maxConcurrent: 5 });

  // 4. 逐条更新 link_status / link_last_checked_at / link_failure_count / folder_id
  //   - 应用第 3 节中的判定与移动逻辑

  return NextResponse.json({ success: true, checked: bookmarks.length });
}
```

> 安全性：该 API 应仅限内部调用（如通过 secret token 或 IP 白名单），避免被普通用户触发。

#### 4.2.2 调度配置

- 每日或每周执行一次全量扫描（按分页跑完全部书签）。  
- 也可以按用户分片（例如每天处理一部分用户）以平衡负载。

### 4.3 管理/调试 API（可选）

提供仅开发/管理员使用的调试接口：
- `POST /api/maintenance/link-check/one`：对单条 bookmark 立即做检测并返回结果，用于调试。

## 5. 前端交互设计（详细）

### 5.1 系统文件夹展示

- 在侧边栏/文件夹列表中，始终显示系统文件夹「失效收藏」：
  - 带数量徽标：`失效收藏（N）`，N 为当前用户 `folder_id = 失效文件夹` 的书签数。
  - 点击进入失效收藏页。

### 5.2 失效收藏页（新建页面或视图）

路由建议：
- `/broken` 或 `/folders/broken` 或作为 `/folders` 子视图中的特殊节点。

展示内容：
- 列表方式显示所有 `folder_id = 失效文件夹 ID` 的收藏：
  - 标题、平台、创建时间、最近检测时间、原文件夹（如有）、评级。  
  - `link_status` 可显示为简短文案：如「404」「超时」「服务器错误」。

支持的操作：

1. **单条恢复**：
   - 操作：「恢复到原文件夹」或「移动到其它文件夹」。
   - 行为：
     - 若 `original_folder_id` 非空且该文件夹仍存在 → 直接移动回 `original_folder_id`。  
     - 否则弹出文件夹选择器，由用户指定新的目标文件夹。  

2. **批量恢复**：
   - 勾选多条 → 统一恢复（同上规则）。  

3. **批量删除**：
   - 支持软删除（沿用现有 delete 行为），用于彻底清理无价值失效内容。  
   - 可增加二次确认提示。

4. **过滤与排序**：
   - 按平台、评级、检测时间排序与过滤。  
   - 可只看「高评级失效收藏」（`importance >= 2`）。  

### 5.3 普通列表中的失效标记

- 在首页/文件夹列表/搜索结果中：
  - 对 `link_status IN ('invalid','timeout','error')` 的条目，在卡片上显示一个小图标：
    - 如「⚠ 已失效」，悬浮提示具体类型（404/500 等）。  
- 点击该标记：
  - 可弹出提示：「该收藏已被系统移动到『失效收藏』目录」，并提供跳转按钮。

### 5.4 搜索页交互

在搜索页面顶部筛选区增加：

- 「链接状态」筛选：
  - 全部  
  - 排除失效收藏（默认）  
  - 仅看失效收藏  

实现方式：
- 在查询参数中增加 `linkStatusFilter`，后端按需过滤 `folder_id` 或 `link_status`。

## 6. 配置项与用户设置

在设置页（`/settings`）增加「链接健康检测」相关配置：

1. **是否启用自动检测**（默认：开启）  
   - 关闭后：后端仍可由管理员手动触发检测，但不再定期跑全量任务。

2. **检测频率**（可简化为文字说明，实际由服务端控制）  
   - 文案示例：「AnyKeep 将每周自动检测你的收藏链接是否失效」。

3. **自动移动策略**（v1 可隐藏，仅在高级设置中提供）  
   - 选项：
     - 自动移动到「失效收藏」文件夹（默认）。  
     - 仅标记为失效，不自动移动（高级用户自选）。

## 7. 实施优先级与开发拆分

### 7.1 后端优先实现清单

1. 数据库迁移：
   - `link_status` / `link_last_checked_at` / `link_failure_count` 字段。  
   - 系统失效文件夹插入逻辑（如 `system_type = 'TRASH_BROKEN_LINKS'`）。  
   - 可选：`original_folder_id` 字段。  

2. 链接检测模块：
   - `src/lib/links/link-checker.ts`（或重构现有 link-validator）。  

3. 定期任务 API：
   - `/api/maintenance/link-check`：接受分页参数，执行一批检测并更新状态。  

4. 状态更新逻辑：
   - 按第 3 节规则更新 `link_status` 等，并负责移动书签到失效文件夹。  

### 7.2 前端实现清单

1. 系统文件夹 UI：
   - 在侧边栏展示「失效收藏」文件夹与数量。  

2. 失效收藏视图：
   - 新页面/路由 + 列表、恢复、批量操作能力。  

3. 普通列表标记：
   - 卡片组件增加失效标志显示逻辑。  

4. 搜索筛选：
   - 在搜索页增加「链接状态」过滤项。  

5. 设置页：
   - 增加基础开关文案（即便暂时不提供复杂配置）。

## 8. 与未来 AI/智能评级等功能的预留

1. 高评级（L2/L3）失效收藏：
   - 后续可在失效视图中强调这类条目，提示用户：
     - 保留笔记  
     - 寻找替代链接  
     - 使用 AI 生成更完整的内容摘要或替代说明。  

2. 与语义搜索的关系：
   - 失效条目仍可以参与语义搜索（尤其是有高质量笔记/摘要的情况）。  
   - 默认搜索结果可下沉或弱化显示失效条目。
