## 二、方案对比

### 方案 A: 物理目录迁移

```
src/app/api/
├── v1/                       # 新版本目录
│   ├── bookmarks/
│   ├── folders/
│   └── ...
├── internal/                 # 保持不变
└── (旧目录作为重定向层)
```

**优点**: 目录结构清晰
**缺点**: 移动 161 个文件，风险高，回滚困难
**工期**: 2 周+

---

### 方案 B: 路径重写（推荐）⭐

```
# 不移动文件，通过 rewrites 实现版本路由
/api/v1/bookmarks/* → /api/bookmarks/*
/api/v1/folders/*   → /api/folders/*
...
```

**优点**:

- 零风险：不改变现有文件
- 利用已有 rewrites 机制
- 秒级回滚
- 兼容现有调用

**缺点**: 物理结构不反映版本

**工期**: 1 周

---

### 方案 C: 混合方案

- 新增 API 放入 `/api/v2/`
- 现有 API 通过 rewrites 提供 `/api/v1/` 访问
- 渐进式迁移

**工期**: 1 周（初始）+ 持续迭代

## 四、详细实施步骤

### 4.1 定义版本常量

```typescript
// src/lib/constants/api-version.ts
export const API_VERSION = {
  current: "v1",
  supported: ["v1"] as const,
  deprecated: [] as const,
} as const;

export type ApiVersion = (typeof API_VERSION.supported)[number];

// 版本化路径生成器
export function versionedPath(
  path: string,
  version: ApiVersion = API_VERSION.current,
): string {
  // /api/bookmarks → /api/v1/bookmarks
  return path.replace("/api/", `/api/${version}/`);
}
```

### 4.2 配置 rewrites 规则

```javascript
// next.config.mjs - rewrites() 新增
async rewrites() {
  return [

    // =====================================================
    // v1 版本路由（指向当前 API）
    { source: '/api/v1/:path*', destination: '/api/:path*' },

    // 保留原有 rewrites...

    { source: '/api/cron/:path*', destination: '/api/internal/cron/:path*' },
    // ...

}
```

### 4.3 更新 api-paths.ts

```typescript
// src/lib/constants/api-paths.ts
import { API_VERSION, versionedPath } from "./api-version";

// 是否启用版本化路径（功能开关）
const USE_VERSIONED_PATHS = process.env.NEXT_PUBLIC_API_VERSIONING === "true";

// 路径生成辅助函数
function apiPath(path: string): string {
  return USE_VERSIONED_PATHS ? versionedPath(path) : path;
}

export const API_BOOKMARKS = {
  list: apiPath("/api/bookmarks"),
  detail: (id: number) => apiPath(`/api/bookmarks/${id}`),
  // ...
} as const;
```

### 4.4 添加版本响应头

```typescript
// src/middleware.ts - 新增版本头
import { API_VERSION } from "@/lib/constants/api-version";

export function middleware(request: NextRequest) {
  const response = NextResponse.next();

  // API 路由添加版本头
  if (request.nextUrl.pathname.startsWith("/api/")) {
    response.headers.set("X-API-Version", API_VERSION.current);
    response.headers.set("X-API-Deprecated", "false");
  }

  return response;
}
```

## 九、决策评估

### 9.1 放弃 API 版本控制的坏处

| 影响维度             | 坏处             | 严重程度 | 说明                               |
| -------------------- | ---------------- | -------- | ---------------------------------- |
| **Breaking Changes** | 无法安全升级 API | 🔴 高    | 任何 API 变更都可能破坏现有客户端  |
| **多版本并存**       | 无法渐进式迁移   | 🔴 高    | 必须「大爆炸」式升级，风险极高     |
| **第三方集成**       | 外部系统集成困难 | 🟡 中    | 浏览器扩展、自动化脚本无法稳定调用 |
| **移动端兼容**       | App 强制更新     | 🟡 中    | API 变更需强制用户更新 App         |
| **调试追踪**         | 版本混淆         | 🟢 低    | 问题排查时难以确定调用的是哪个版本 |
| **文档维护**         | 无版本标识       | 🟢 低    | OpenAPI 文档缺少版本信息           |

**结论**: 对于**当前阶段**的 AnyKeep（单一 Web 应用、无第三方集成），放弃版本控制的**实际影响较小**。

### 9.2 完成 API 版本控制的好处

| 影响维度       | 好处             | 收益程度 | 说明                             |
| -------------- | ---------------- | -------- | -------------------------------- |
| **未来扩展**   | 为 v2 预留通道   | 🔴 高    | 未来 breaking changes 有安全路径 |
| **浏览器扩展** | 稳定集成基础     | 🔴 高    | Phase 3 扩展开发的前提条件       |
| **API 开放**   | 第三方接入基础   | 🟡 中    | 未来开放 API 的必要条件          |
| **多端支持**   | 移动端独立迭代   | 🟡 中    | Web/App 可使用不同版本           |
| **专业度**     | 工程规范提升     | 🟢 低    | 符合行业最佳实践                 |
| **文档完善**   | OpenAPI 版本标识 | 🟢 低    | 文档更清晰专业                   |

**结论**: 如果计划开发**浏览器扩展**或**开放 API**，版本控制是**必要前提**。

## 十、决策建议

### 场景 A: 仅 Web 应用（当前）

**建议**: ⏸️ **暂缓实施**

- 当前架构升级完成度 94%，版本控制非阻塞项
- 投入 1 周工期，收益有限
- 可在开发浏览器扩展前再实施

### 场景 B: 计划开发浏览器扩展

**建议**: ✅ **立即实施**

- 扩展需要稳定的 API 契约
- 扩展和 Web 可能使用不同版本
- 1 周工期，为 Phase 3 扩展开发打基础

### 场景 C: 计划开放 API

**建议**: ✅ **必须实施**

- 外部开发者依赖版本稳定性
- 需要版本废弃通知机制
- 是 API 开放的行业标准

---

**最终决策**: 请根据未来 3-6 个月的产品规划选择实施时机。
