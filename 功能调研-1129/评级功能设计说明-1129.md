## 评级功能设计说明（AnyKeep）

**文档日期**：2025-11-29  
**文档版本**：V1.0

---

## 1. 背景与目标

### 1.1 背景

当前 AnyKeep 已具备：

- **跨平台收藏**：微信 / B 站 / 小红书 / 浏览器书签等统一存储在 `bookmarks`。
- **AI 能力**：摘要、标签、智能分类、重分类。
- **基础搜索与管理**：关键词/全文搜索、文件夹、标签、批量操作。

但在长期使用中，用户会遇到这些问题：

- 收藏量上来后，「真正重要的那几条」容易被淹没在信息流中。
- 对内容的使用方式不同（一次性参考 vs 需要深入学习），目前都被同等对待。
- 复盘/学习功能缺乏抓手，很难知道「哪些是我应该多看几次的内容」。

### 1.2 设计目标

**核心目标**：为每条收藏增加一个轻量的「评级」维度，服务三个具体目的：

1. **分级管理 & 易于筛选高价值收藏**
   - 支持用户显式区分：一般参考 / 高价值 / 深度学习内容。
   - 可以在列表和搜索中快速筛出高价值内容。

2. **围绕高价值收藏提供更多附加功能**
   - 针对高价值收藏（尤其是核心知识），在详情页与列表中给予更强支持：
     - 置顶/优先展示
     - 更方便地加入专题/任务

3. **配合复盘/学习**
   - 对需要多次复盘的内容（如系统性教程），提供简单的「学习/复盘」机制：
     - 知道哪些条目需要多看几次
     - 在合适的时间提醒复盘

## 2. 评级模型设计

### 2.1 评级档位

采用 **4 档、语义清晰** 的评级模型，而非纯数字星级：

- **L3：深度学习（需要多次复盘）**
  - 典型：系统性教程、方法论拆解、工作流/体系类内容。
  - 含义：值得多次学习、做笔记、实战应用。

- **L2：高价值（需要优先关注）**
  - 典型：高质量案例、关键灵感、重要参考资料。
  - 含义：近期可能用到，优先阅读/优先保留。

- **L1：一般/可参考**
  - 典型：一次性参考、可能有用的链接。
  - 含义：可以保留，在需要时通过搜索找到即可。

- **L0：未评级**
  - 默认状态。
  - 含义：尚未显式评估价值，行为上与 L1 接近，但在高价值视图中会被过滤掉。

### 2.2 与目标的对应关系

- **分级管理**：主要使用 L1/L2/L3（L0 为默认态）。
- **高价值附加功能**：重点针对 L2/L3。
- **复盘/学习**：主要针对 L3。

## 3. 数据模型与数据库设计

### 3.1 字段设计

在 `public.bookmarks` 表中新增字段（示例）：

```sql
ALTER TABLE public.bookmarks
ADD COLUMN importance SMALLINT NOT NULL DEFAULT 0;

COMMENT ON COLUMN public.bookmarks.importance IS '重要程度评级: 0-未评级, 1-一般, 2-高价值, 3-深度学习';
```

- **取值约定**：
  - `0` → L0：未评级
  - `1` → L1：一般/可参考
  - `2` → L2：高价值
  - `3` → L3：深度学习

> **可选增强**：后续可用 CHECK 约束限制取值范围：`CHECK (importance BETWEEN 0 AND 3)`。

### 3.2 索引与性能

根据后续查询场景，建议增加索引：

```sql
CREATE INDEX idx_bookmarks_importance
ON public.bookmarks (importance)
WHERE deleted_at IS NULL;
```

- 用途：
  - 列表页筛选高价值 (`importance >= 2`)。
  - 学习/复盘队列选择 L3 条目。

## 4. API 设计与改造点

### 4.1 创建收藏 API（POST `/api/bookmarks`）

- **当前行为**：
  - 未显式设置评级字段。
- **改造建议**：
  - 请求体可选字段：`importance?: number`。
  - 若前端未传，则使用默认值 `0`。

**校验规则**：

- `importance` 必须在 `[0, 3]` 内，否则拒绝或重置为 0。

### 4.2 更新收藏 API（PUT `/api/bookmarks/[id]`）

- 支持单独更新 `importance` 字段：
  - 前端可在详情页直接发送仅包含 `importance` 的 PATCH/PUT。
- 建议在 Zod/类型层增加校验：
  - 仅允许数值 0–3。

### 4.3 批量操作 API（可选增强）

如果已有批量移动/删除接口，可增加 **批量设置评级** 的 API：

- **API 示例**：`POST /api/bookmarks/batch-update-importance`
- **请求体示例**：

```json
{
  "bookmarkIds": [1, 2, 3],
  "importance": 2
}
```

- **行为**：
  - 对指定 `bookmarkIds` 批量设置同一评级。
  - 按现有 RLS 策略校验 user_id。

### 4.4 搜索与列表 API

在现有列表/搜索接口中增加：

- 可选查询参数：
  - `minImportance`（只返回 >= 某级别的收藏）
  - `importance`（精确过滤指定等级）
  - `orderBy=importance_desc_created_at`（按评级+时间排序）

**示例**：

- `/api/bookmarks?minImportance=2` → 高价值视图（L2/L3）。
- `/api/bookmarks?importance=3` → 深度学习队列。

在 SQL 层：

- `WHERE importance >= $minImportance`。
- `ORDER BY importance DESC, created_at DESC`。

## 5. 前端交互与 UI 设计

### 5.1 列表卡片上的评级操作

**目标**：使评级成为一个「极轻量」的操作。

- 在每个 `BookmarkCard` 上增加一个小图标/标记（例如小旗帜/小徽章）。
- 点击行为：
  - 单击循环切换：L0 → L1 → L2 → L3 → L0。
  - 即时调用更新 API，或加入乐观更新 + 后台请求。

**视觉建议**：

- L0：不显示或灰色图标。
- L1：浅色标记（不抢眼，表示“已看过，但一般”）。
- L2：明显颜色（如蓝色/绿色），提示是「高价值」。
- L3：高亮颜色（如金色/橙色），可以配一个小「📘/🎓」类视觉暗示「学习型内容」。

### 5.2 详情页中的评级组件

- 在详情页标题区域（靠近平台标记）显示完整评级控件：
  - 文字 + 图标，例如：
    - 「未评级」
    - 「一般 · 可参考」
    - 「高价值」
    - 「深度学习 · 多次复盘」
- 支持点击弹出一个轻量选择框（或同样使用点击循环切换）。

> 详情页是用户「认真读完之后」最容易打评级的位置。

### 5.3 列表/搜索视图的筛选与排序

在首页、搜索页的筛选区域增加：

- **筛选项**：
  - 重要程度：
    - 全部
    - 高价值（L2+）
    - 深度学习（L3）
- **排序项**：
  - 默认：按时间
  - 按「重要程度 + 时间」排序（`importance DESC, created_at DESC`）

## 6. 围绕评级的功能联动设计

### 6.1 高价值收藏的附加功能（L2/L3）

1. **列表优先展示**
   - 在常规列表中：
     - 同一文件夹/标签下，可选择「优先展示高价值」。
   - 高价值内容可以在顶部区域单独显示一个小区块：
     - 「本文件夹的高价值收藏（前 N 个）」。

2. **专题/项目入口**
   - 针对 L2/L3 收藏，在详情页中增加：
     - 「加入专题」入口：快速将该条收藏加入某个学习专题/项目。
     - 「添加行动项」入口：一键生成 TODO/任务。

### 6.2 学习与复盘机制（重点 L3）

**只对 L3 做「学习/复盘队列」，以避免负担过重。**

1. **复盘队列视图**
   - 在首页或单独一个 tab：
     - 「学习 / 复盘」视图，列出所有 L3 收藏。
   - 按状态分组：
     - 未开始 / 进行中 / 待复盘 / 已掌握。

2. **轻量复习节奏**
   - 初版可采用简单规则（不需要完整间隔重复算法）：
     - 设为 L3 当天 → 标记为「未开始」。
     - 完成初次阅读后，用户可标记为「已看一次」，自动计算 3 天后复盘。
     - 复盘后可提示再过 7–14 天做一次巩固。

3. **首页提醒**
   - 在首页顶部或 analytics 页增加：
     - 「今日建议复盘」：列出少量 L3 收藏。

### 6.3 搜索与推荐中的权重调整

- 在语义搜索与混合搜索排序中：
  - 将 `importance` 作为一个额外权重：
    - L3 得分加成 > L2 > L1/L0。
- 这样，在用户检索时：
  - 自己标记为高价值的内容，会比普通收藏更容易出现在前几条结果中。

## 7. MVP 范围与迭代计划

### 7.1 评级 MVP 范围（P0）

**P0 实现目标**：先打通「分级管理 + 筛选 + 排序」，不直接上复盘机制。

- 后端：
  - `bookmarks.importance` 字段 + 索引。
  - 创建/更新 API 支持 `importance` 字段。
  - 列表/搜索 API 支持按 `importance` 过滤和排序。
- 前端：
  - 列表卡片 + 详情页的评级 UI（循环切换）。
  - 列表/搜索页的「高价值筛选」与「按重要程度排序」。

### 7.2 P1：高价值附加功能

- 高价值内容置顶区块（文件夹/首页各一块简易视图）。
- 详情页对 L2/L3 增强「加入专题/任务」入口。

### 7.3 P2：学习与复盘机制

- L3 复盘队列视图。
- 简单复盘节奏与首页「今日复盘」提醒。
- 在搜索/推荐权重中显式加入评级因子。

## 8. 智能评级扩展方案（基于阿里百炼 & DeepSeek）

> 本节为《智能评级功能设计-ali-deepseek-1129》的概要集成，用于说明如何在现有手动评级模型上叠加 AI 建议能力。

### 8.1 设计思路

- 在保留 `importance` 手动评级为主的前提下，引入 AI 建议字段：
  - `importance_ai_suggested`：AI 推荐评级（1/2/3）。
  - `importance_ai_reason`：AI 给出的中文理由。
  - `importance_ai_confidence`：AI 推荐置信度（0–1）。
- 真实生效的评级只写入 `importance`，AI 仅供参考，由用户一键接受/调整。

### 8.2 字段扩展

在第 3 节基础上，新增：

```sql
ALTER TABLE public.bookmarks
ADD COLUMN importance_ai_suggested SMALLINT,
ADD COLUMN importance_ai_reason TEXT,
ADD COLUMN importance_ai_confidence REAL;
```

用途：

- 存储 DeepSeek / 阿里百炼输出的推荐结果。
- 支持前端展示「AI 推荐评级」模块。

### 8.3 AI 输入与输出协议

- **输入特征**：
  - 标题、平台类型、AI 摘要、AI 标签、用户标签、（可选）文件夹路径。
  - 后续可以加入行为特征：打开次数、最近访问时间、笔记长度等。
- **输出 JSON 结构**（统一 DeepSeek / 百炼）：

```json
{
  "importance_suggested": 2,
  "reason": "该内容是系统性教程的一部分，信息密度高，且用户写了较长笔记，建议标记为高价值（L2）。",
  "confidence": 0.82
}
```

### 8.4 与阿里百炼 & DeepSeek 的集成方式（概要）

- **DeepSeek**：
  - 用作主力模型，调用 `deepseek-chat`。
  - Prompt：说明 L1/L2/L3 含义，给出收藏特征摘要，要求输出 JSON。
- **阿里百炼（通义千问）**：
  - 用作 fallback 或需要走阿里云场景的主力。
  - Prompt 与 DeepSeek 共用定义，只强调「只能输出 JSON」。
- 两者都通过同一解析逻辑写入 `importance_ai_*` 字段。

详细 Prompt 与调用示例见独立文档《智能评级功能设计-ali-deepseek-1129》。

### 8.5 前端交互整合

- 在详情页增加「AI 推荐评级」区域（仅当存在 `importance_ai_suggested` 时展示）：
  - 文案示例：
    - 「AI 推荐：高价值（L2）」  
      理由：……  
      按钮：[接受推荐] [改为一般] [改为深度学习]
- 列表中可以用小图标标记「有 AI 建议」的条目（可选）。
- 一旦用户点击「接受」或选择其他等级：
  - 更新 `importance` 字段为相应档位。
  - 可选择清空或保留 AI 建议信息（建议保留，供审计与后续分析）。

### 8.6 触发策略（MVP）

- **Phase 1**：仅在「新建收藏成功后」异步触发 AI 建议：
  - 不阻塞收藏创建流程。
  - 用户稍后打开详情页即可看到推荐。
- **Phase 2**：基于行为信号的「事后建议」：
  - 例如「最近经常打开但未标记为高价值的收藏」列表。
  - 可以无需再次调用大模型，仅用规则 + 现有 AI 摘要即可。

## 8. 风险与注意事项

1. **用户心智与负担**
   - 不强迫用户为所有收藏评级，默认保持 L0 即可。
   - 交互要足够轻量：1–2 次点击即可完成评级。

2. **与标签/文件夹的关系**
   - 评级不是分类，而是「重要性维度」。
   - 文案和 UI 上避免与标签/文件夹混淆。

3. **兼容升级**
   - 现有数据全部默认 `importance = 0`。
   - 后续可考虑根据历史行为（打开次数、是否有长笔记）给出「推荐评级」，但不在本版范围内强行自动调整。
