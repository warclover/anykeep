## 一、��计理念

### 核心洞察

一次性导入 1000 个收藏与日常单个收藏的逻辑完全不同：

- **单个收藏** = "向已知的架子上摆书"
- **批量导入** = "面对一地乱书，重新设计图书馆的布局"

### 设计原则

1. **不追求即时性，追求全局视野下的合理性**
2. **先做好自动分组，起名字的事可以交给用户**
3. **渐进式信任**：沙盒预览 → 用户确认 → 批量应用
4. **功能解耦**：各模块独立运行，通过接口协作

## 三、核心流程：三步分拣法

### Phase 1: 特征批处理 (Bulk Feature Extraction)

**目标**: 将书签转化为可计算的向量表示，不做任何分类决策

#### 3.1.1 处理内容

1. 全部书签存入临时导入池，标记 `status: 'processing'`
2. 批量提取元数据特征：

```typescript
interface MetadataFeatures {
  title: string;
  keywords: string[];           // <meta name="keywords">
  description: string;          // <meta name="description">
  ogTags: Record<string, string>; // Open Graph 标签
  domain: string;               // 域名作为特征
  meaningfulDomain: string;     // 语义域名（如 github.com/facebook）
  platform: 'github' | 'zhihu' | 'weixin' | 'bilibili' | 'xiaohongshu' | 'other';
}
```

3. **L1.5 标签预分组**（新增）
4. 分批生成向量嵌入（每批 50 个，批次间隔 2 秒）

#### 3.1.2 L1.5 标签预分组（新增）

**目标**: 在向量计算前，利用网页自带 keywords 进行预分组，减少后续计算量

```typescript
interface PreGroupingService {
  // 按关键词预分组
  async preGroupByKeywords(bookmarks: Bookmark[]): Promise<PreGroupingResult>;
}

interface PreGroupingResult {
  groups: Map<string, string[]>;  // keyword -> bookmarkIds
  ungrouped: string[];            // 无标签的书签
  superNodes: SuperNode[];        // 聚合后的超级节点
}

interface SuperNode {
  id: string;                     // group:${keyword}
  embedding: number[];            // 代表向量
  memberIds: string[];            // 成员书签 ID
  weight: number;                 // 权重 = 成员数
}
```

**实现逻辑**:

```typescript
async function preGroupByKeywords(bookmarks: Bookmark[]): Promise<PreGroupingResult> {
  const groups = new Map<string, string[]>();
  const ungrouped: string[] = [];

  for (const bookmark of bookmarks) {
    const keywords = bookmark.metadata?.keywords || [];

    if (keywords.length > 0) {
      const primaryKeyword = normalizeKeyword(keywords[0]);
      if (!groups.has(primaryKeyword)) {
        groups.set(primaryKeyword, []);
      }
      groups.get(primaryKeyword)!.push(bookmark.id);
    } else {
      ungrouped.push(bookmark.id);
    }
  }

  // 将 10+ 个同标签书签合并为"超级节点"
  const superNodes: SuperNode[] = [];
  for (const [keyword, ids] of groups) {
    if (ids.length >= 10) {
      const representative = await selectRepresentative(ids);
      superNodes.push({
        id: `group:${keyword}`,
        embedding: representative.embedding,
        memberIds: ids,
        weight: ids.length,
      });
    }
  }

  return { groups, ungrouped, superNodes };
}
```

**成本节省估算**:

| 场景 | 原方案 | L1.5 优化后 | 节省 |
|-----|-------|------------|------|
| 1000 书签，30% 有重复标签 | 1000 次向量对比 | ~700 次 | 30% |
| 极端情况：50% 标签重复 | 1000 次 | ~500 次 | 50% |

### Phase 2: 无监督聚类 (Unsupervised Clustering)

**目标**: 在不看用户现有文件夹的情况下，发现书签内部的"小圈子"

#### 3.2.1 自适应聚类算法（更新）

**问题**: DBSCAN 对 `eps` 参数极其敏感
- eps 太大 → 2-3 个巨大的"杂货堆"
- eps 太小 → 几百个 1-2 篇的"碎屑"

**解决方案**: HDBSCAN 优先 + 迭代式 DBSCAN 兜底

```typescript
interface ClusteringStrategy {
  primary: 'hdbscan';           // 首选：自动发现多密度簇
  fallback: 'iterative-dbscan'; // 兜底：轻量级迭代方案

  hdbscanConfig: {
    minClusterSize: 3;          // 最小簇大小
    minSamples: 2;              // 核心点邻域最小样本数
    clusterSelectionMethod: 'eom'; // 'eom' | 'leaf'
  };

  iterativeDbscanConfig: {
    initialEps: 0.2;
    epsStep: 0.05;
    maxIterations: 5;
    targetClusterRatio: 0.7;    // 目标：70% 书签被成簇
  };
}
```

**自适应聚类实现**:

```typescript
async function adaptiveClustering(embeddings: number[][]): Promise<Cluster[]> {
  // 优先尝试 HDBSCAN
  try {
    const hdbscan = await import('hdbscan');
    return hdbscan.cluster(embeddings, {
      minClusterSize: 3,
      minSamples: 2,
    });
  } catch (e) {
    // 降级到迭代式 DBSCAN
    return iterativeDbscan(embeddings, {
      targetClusterRatio: 0.7,
    });
  }
}

function iterativeDbscan(embeddings: number[][], config: IterativeConfig): Cluster[] {
  let eps = 0.2;
  let clusters: Cluster[];

  for (let i = 0; i < config.maxIterations; i++) {
    clusters = dbscan(embeddings, eps, minPts: 2);
    const clusterRatio = 1 - (clusters.noise.length / embeddings.length);

    if (clusterRatio >= config.targetClusterRatio) {
      return clusters;
    }
    eps += 0.05;  // 放大半径
  }

  return clusters;  // 返回最后一次结果
}
```

#### 3.2.2 域名协同权重（新增）

**问题**: 仅依靠向量可能丢失关联信息（如 20 个 GitHub 链接逻辑上都属于"技术"）

**解决方案**: 分级域名权重

```typescript
interface DomainWeightConfig {
  // 域名类型分类
  domainCategories: {
    professional: ['github.com', 'stackoverflow.com', 'developer.mozilla.org'];
    contentPlatform: ['medium.com', 'zhihu.com', 'juejin.cn', 'bilibili.com'];
    portal: ['news.google.com', 'hao123.com'];
    shortener: ['bit.ly', 't.co', 'tinyurl.com'];
  };

  // 距离调整因子
  distanceModifiers: {
    professional: -0.15;     // 同一专业站点，距离减少 15%
    contentPlatform: -0.05;  // 内容平台，轻微减少 5%
    portal: 0;               // 门户不调整
    shortener: 0;            // 短链忽略
  };
}

function computeAdjustedDistance(
  a: Bookmark,
  b: Bookmark,
  rawDistance: number
): number {
  if (a.domain === b.domain) {
    const category = getDomainCategory(a.domain);
    const modifier = distanceModifiers[category];
    return Math.max(0, rawDistance + modifier);
  }
  return rawDistance;
}
```

**子域名智能处理**:

```typescript
function extractMeaningfulDomain(url: string): string {
  const parsed = new URL(url);

  // GitHub/GitLab：使用 org 级别
  if (['github.com', 'gitlab.com'].includes(parsed.hostname)) {
    const [org] = parsed.pathname.split('/').filter(Boolean);
    return `${parsed.hostname}/${org}`;  // github.com/facebook
  }

  // 其他：使用主域名
  return parsed.hostname;
}
```

#### 3.2.3 分层采样聚类

```
第一轮：随机采样 10%（100 个）做全量 HDBSCAN/DBSCAN
       → 发现 K 个粗粒度簇

第二轮：剩余 900 个只需计算与 K 个簇质心的距离
       → 复杂度从 O(n²) 降到 O(n×k)

第三轮：对每个粗粒度簇内部再做细粒度聚类
       → 发现子结构（支持文件夹嵌套）
```

**性能对比**:

| 方案 | 1000 个书签的计算量 | 准确率 |
|-----|-------------------|-------|
| 全量 DBSCAN | ~500,000 次距离计算 | 100% |
| 向量降维方案 | ~500,000 次（低维） | ~85% |
| **分层采样（采用）** | ~50,000 次（全维） | ~95% |

**复用现有代码**:
- `DBSCAN` 聚类算法（扩展为 HDBSCAN）
- `computeSimilarityMatrix()` 相似度矩阵
- `cosineSimilarity()` 余弦相似度

### Phase 3: 映射与生长 (Mapping & Growth)

**目标**: 将聚类结果与用户现有文件夹匹配，或触发新文件夹创建

#### 3.3.1 映射策略分级

| 匹配程度 | 条件 | 动作 |
|---------|------|------|
| 精准匹配 | 簇质心与文件夹质心相似度 > 0.75 | 直接归档 |
| 模糊匹配 | 相似度 0.5-0.75 | 列入"建议归档"，需用户确认 |
| 无匹配 | 相似度 < 0.5 | 触发晶体生长，新建文件夹 |
| 目标混乱 | 目标文件夹内聚度 < 0.4 | 建议新建而非合并 |

**核心映射逻辑**:

```typescript
async function mapClustersToExistingFolders(
  clusters: Cluster[],
  existingFolderProfiles: FolderProfile[]
): Promise<MappingResult[]> {
  const mappingResults: MappingResult[] = [];

  for (const cluster of clusters) {
    // 1. 计算簇的平均向量 (Centroid)
    const clusterCentroid = calculateMeanVector(cluster.embeddings);

    // 2. 在现有文件夹向量库中搜索
    const bestMatch = await findMostSimilarFolder(clusterCentroid, existingFolderProfiles);

    // 3. 检查目标文件夹是否混乱
    const targetCohesion = bestMatch ? await computeFolderCohesion(bestMatch.id) : 0;

    if (bestMatch && bestMatch.similarity > 0.75 && targetCohesion > 0.4) {
      // 精准匹配：直接归档
      mappingResults.push({
        clusterId: cluster.id,
        action: 'MERGE',
        targetId: bestMatch.id,
        confidence: bestMatch.similarity,
      });
    } else if (bestMatch && bestMatch.similarity > 0.5) {
      // 模糊匹配：需用户确认
      mappingResults.push({
        clusterId: cluster.id,
        action: 'SUGGEST_MERGE',
        targetId: bestMatch.id,
        confidence: bestMatch.similarity,
        warning: targetCohesion < 0.4 ? 'target_folder_messy' : undefined,
      });
    } else {
      // 无匹配：晶体生长，新建文件夹
      const suggestedName = await generateFolderNameViaLLM(cluster.sampleTitles);
      mappingResults.push({
        clusterId: cluster.id,
        action: 'CREATE',
        name: suggestedName,
        confidence: cluster.cohesion,
      });
    }
  }

  return mappingResults;
}
```

#### 3.3.2 L3 代表元命名（优化）

function selectRepresentativeSamples(cluster: Bookmark[]): {
  core: Bookmark[];
  edge: Bookmark[];
} {
  const sorted = cluster.sort((a, b) =>
    distanceToCentroid(a) - distanceToCentroid(b)
  );

  return {
    core: sorted.slice(0, 3),     // 3 个最靠近质心（核心内容）
    edge: sorted.slice(-2),       // 2 个最远离质心（边界内容）
  };
}

async function undoBatchImport(batchId: string): Promise<void> {

  if (!transaction.undoAvailable) {

}

## 五、成本控制：异步漏斗机制

### L1: 元数据先行 ✅

优先使用零成本的元数据进行初筛：

- `<title>` 标签
- `<meta name="keywords">`
- `<meta name="description">`
- Open Graph 标签
- URL 域名和平台识别

### L1.5: 标签预分组 ✅（新增）

- 在向量计算前，按 keywords 预分组
- 10+ 个同标签书签合并为"超级节点"
- 减少 30%-50% 向量对比计算量

### L2: 分层采样聚类 ✅

- 不降维，保持语义精度
- 采样 10% 做全量聚类
- 剩余 90% 只计算与簇质心距离
- 复杂度从 O(n²) 降到 O(n×k)

### L3: 代表元命名 ✅（优化）

- 不给 1000 个书签都请 AI 分类
- 每个聚类只请一次 AI
- 选取 3 个核心 + 2 个边界样本
- 1000 个书签预计只需 10-20 次 AI 调用

**成本估算**（1000 个书签）:

| 项目 | 调用次数 | 单价 | 成本 |
|-----|---------|------|------|
| 向量嵌入 | ~700（L1.5 优化后） | $0.0001/个 | $0.07 |
| AI 命名 | ~15 | $0.01/次 | $0.15 |
| **总计** | - | - | **~$0.22** |

## 附录：关键决策记录

| 决策点 | 选项 | 决策 | 理由 |
|-------|------|------|------|
| 聚类算法 | DBSCAN vs K-Means vs HDBSCAN | **HDBSCAN 优先** | 自动发现多密度簇，无需手动调参 |
| eps 敏感性 | 固定值 vs 自适应 | **迭代式自适应** | 避免极端聚类结果 |
| 域名权重 | 统一权重 vs 分级权重 | **分级权重** | 专业站点 vs 内容平台差异大 |
| 降维方案 | 384 维降维 vs 分层采样 | **分层采样** | 保持精度，降低复杂度 |
| 预分组 | 无 vs L1.5 标签预分组 | **标签预分组** | 节省 30%-50% 计算量 |
| 去重时机 | 分拣中 vs 分拣后 | **分拣后独立** | 不阻塞主流程 |
| 命名策略 | 全量 AI vs 代表样本 | **核心+边界代表元** | 成本控制 + 概括性 |
| 确认机制 | 自动应用 vs 用户确认 | **沙盒预览 + 确认** | 渐进式信任 |
| 冲突处理 | 静默覆盖 vs 高亮展示 | **高亮 + 用户选择** | 尊重用户原有结构 |
| 撤销机制 | 无 vs 24h 窗口 | **24h 可撤销** | 降低用户心理压力 |
| 确认模式 | 列表 vs 卡片流 | **混合模式** | 高冲突时自动切换卡片流 |
