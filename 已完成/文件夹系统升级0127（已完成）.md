### 唯一缺失的环节

**重命名时没有自动保留旧名称为别名。**

```
当前流程：
用户把 "代码" 改成 "开发"
    ↓
系统更新 folders.name = "开发"
    ↓
"代码" 这个词丢失了 ❌
    ↓
下次遇到 "代码相关" 的书签，无法匹配到这个文件夹
```

---

## 二、解决方案

### 极简实现：一行代码

在重命名 API 中，调用现有的 `FolderAliasManager.addAlias()` 方法：

```
改进后流程：
用户把 "代码" 改成 "开发"
    ↓
系统更新 folders.name = "开发"
    ↓
【新增】调用 addAlias("代码") ✅
    ↓
"代码" 保存到 folder_tag_profiles.aliases
    ↓
下次遇到 "代码相关" 的书签，仍能匹配（置信度 0.95）
```

### 4.2 新增辅助函数

**文件**：`src/lib/classification/folder-profile-manager.ts`

```typescript
import { FolderAliasManager } from "./strategies/modern/folder-alias-manager";

/**
 * 重命名时保留旧名称为别名
 * @param folderId 文件夹 ID
 * @param oldName 旧名称
 * @param userId 用户 ID
 */
export async function preserveOldNameAsAlias(
  folderId: number,
  oldName: string,
  userId: string
): Promise<void> {
  const aliasManager = FolderAliasManager.getInstance();

  // 确保 folder_tag_profiles 记录存在
  await ensureFolderTagProfileExists(folderId, userId);

  // 添加旧名称为别名
  await aliasManager.addAlias(userId, folderId, oldName);

  logger.info({ folderId, oldName }, "Preserved old folder name as alias");
}

/**
 * 确保 folder_tag_profiles 记录存在（如果不存在则创建）
 */
async function ensureFolderTagProfileExists(folderId: number, userId: string): Promise<void> {
  const supabase = await createServerClient();

  await supabase
    .from("folder_tag_profiles")
    .upsert({
      user_id: userId,
      folder_id: folderId,
      aliases: [],
      core_tags: [],
      related_tags: [],
    }, {
      onConflict: "user_id,folder_id",
      ignoreDuplicates: true,
    });
}
```

### 4.3 可选优化：别名去重

**修改 FolderAliasManager.addAlias() 方法**（如果尚未去重）：

```typescript
async addAlias(userId: string, folderId: number, alias: string): Promise<void> {
  const normalizedAlias = tagNormalizer.normalize(alias);

  // 先检查是否已存在
  const { data: existing } = await this.supabase
    .from("folder_tag_profiles")
    .select("aliases")
    .eq("user_id", userId)
    .eq("folder_id", folderId)
    .single();

  if (existing?.aliases?.includes(normalizedAlias)) {
    return; // 已存在，跳过
  }

  // 追加别名
  await this.supabase
    .from("folder_tag_profiles")
    .update({
      aliases: [...(existing?.aliases || []), normalizedAlias]
    })
    .eq("user_id", userId)
    .eq("folder_id", folderId);
}
```

### 5.2 边界情况处理

| 场景 | 处理方式 |
|------|----------|
| 重复别名 | `addAlias` 内部去重 |
| folder_tag_profiles 不存在 | `ensureFolderTagProfileExists` 自动创建 |
| 名称相同（无变化） | 跳过，不添加别名 |
| 系统文件夹 | 现有逻辑已阻止重命名 |

## 六、不做的事情（YAGNI）

| 功能 | 理由 |
|------|------|
| ~~别名权重衰减~~ | 过度设计，先保留所有历史名称 |
| ~~别名数量上限~~ | 用户不会频繁改名，无需限制 |
| ~~sync_status 状态机~~ | 不需要异步同步，直接写入 |
| ~~定时任务~~ | 不需要，改名时立即写入 |
| ~~LLM 同义词生成~~ | 用现有标签数据替代 |
| ~~自动拆分/合并~~ | 风险太高，保持建议模式 |
| ~~EventEmitter 事件系统~~ | 过度设计 |

## 十一、设计原则回顾

### 为什么这个方案是正确的？

| 原则 | 体现 |
|------|------|
| **KISS** | 复用现有系统，不引入新架构 |
| **YAGNI** | 只做必要的功能，砍掉所有"未来可能需要"的设计 |
| **DRY** | 复用 `FolderAliasManager`，不重复实现 |
| **用 SQL ���代 AI** | 利用现有别名匹配机制，不调用 LLM |

### 核心思想

> **改名即记忆**：用户把"代码"改成"开发"，系统自动记住"代码"这个词。下次遇到"代码相关"的书签，仍然能匹配到这个文件夹。
